## 实现与正确性

indexer 对四个 token 组成的完整组评分，余下 0..3 个 token 单独参加 attention。
图选择使用 `floor(exclusive_end/4)*4`。这使分档边界后的一到三个 token
无需切到更大的 score 矩阵，且没有遗漏任何完整因果组。
KV 总容量、token 位置、稀疏预算和尾部处理均保持原规则。
六个边界、单 token/128-token 共 24 组对照的 ID/mask 逐元素一致。
32k、256k 分布检索与重复文档的零 prefill 缓存检查通过。

最终采用 r86，实际捕获容量为 [16384, 32768, 65536, 98304, 131072, 196608, 262144]。
四档与七档均实测；接近的成绩优先选择四档，以减少启动捕获和常驻缓冲。

## 连续请求的缓存显存修复

最初七档版本虽然单次 256k 通过，但紧接新 8k 请求会在 worker 的 eager
MoE 临时分配处 OOM。旧的满长文 GPU 快照仍占着显存，直到新请求 prefill
完成才淘汰；额外图缓冲使这项旧策略超过了可用显存余量。

r89 将已满缓存的 LRU 未命中淘汰提前到 prefill 前，并添加 worker release RPC。
worker 不再用循环局部变量额外持有上一次保存的快照。命中的状态不提前淘汰，
精确重复请求仍为零 prefill。r90 对继续追问先加载命中的状态，再在 prefill 前
释放将被替换的 LRU 槽和当前请求的局部引用。缓存只是被提前淘汰，不改变模型计算或输入。
策略单测覆盖命中、未命中、LRU 顺序、未满/禁用缓存、继续追问以及状态引用释放。
修复后按 256k→原文重复→三次新 8k→第二个新 256k→原文重复→长文追问顺序测试通过。
长文追问的输入 262045 tokens，新增 prefill
29 tokens，回答 '7319'，
服务 TTFT 0.587 秒。
失败日志保留为 `benchmarks/r87/before-fix-oom.log`，不以单次成功代替连续请求检查。

已改用与服务一致的模板与分词流程，原始测试中断日志也随证据保存。
