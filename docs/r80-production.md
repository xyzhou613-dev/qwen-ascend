## 采用的实现

- 第二阶段的输出头与 greedy argmax 合入 decode 计算图。
- 专家量化 scale 装载时预计算，保留原 BF16 数值，释放原始 scale，净增每元素 1 字节。
- decode down projection 使用选中专家 GMM；gate/up 保留原实现。
- 专家 SwiGLU 保持 FP32 中间计算并融合。
- indexer 按位置选择 16k/64k/128k/256k 图，跳过因果不可见的未来 key。
- 所有捕获使用同一显式 stream，串行图共享内存池。
- 8192-token prefill 块；FP32 DeltaNet 临时准备按 2048 窗口分批。
- 原生稀疏 attention 用 K_nonrope(192)+V(256)+zero(64) 的 512 维 latent，
  query 在 V 对应位置补零，64 维 RoPE 单独传入，输出取 latent 的 192:448。
  两个 KV 头独立执行，12 个 query 头补到 16。
- 同时保存位置优先的原始 KV 与 packed latent；prefill 使用原生稀疏接口，
  decode 直接读取原始 KV。所有写入、快照、重置、恢复均覆盖两种表示。
  256k 每卡额外 3 GiB，完整 GPU 对话快照再额外 3 GiB。
- 缓存整个已配置位置范围的 BF16 RoPE sin/cos，逐元素一致性与动态图测试通过。

## 验收与边界

200-token teacher forcing：mean_nll=2.165267，ppl=8.7169，
top1=0.485；参考 NLL 2.164792，门限保持 ±0.01。
三处事实位于约 10%、50%、90%，检索 3/3；相同文档重复请求 prefill=0 且检索正确。
最终部署后重新跑了全新 256k、128 输出及三次全新 8k，日志 FINAL_PRODUCTION_ACCEPT。
运行模块与 Git 模块的 AST 全部相同，health 额外公开部署选项。

微基准与边界检查包括：scale 逐元素一致；indexer 12 组边界 ID/mask 一致；
RoPE 随机/边界位置、BF16/FP32 和动态图一致；双 KV 写入与直接 decode 一致；
FP32 窗口在随机/强相关、8192/16384 输入上与已部署 8192 路径逐元素一致。

## 排除的方案

- QSA tile 256：完整 256k 仅约 0.3 秒变化，未作为确定收益。
- 未分批的 16384：FP32 准备阶段 OOM；分批后跑通但端到端慢于 8192。
- PyPTO FP32 递推：微基准及 256 步状态误差很小，完整模型 NLL 2.181862
  超过门限，未提交/部署该计算路径。
- PyPTO mixer：修复四路求和顺序与 BF16 舍入后逐元素一致，但 96 次调用
  1.59 ms -> 2.87 ms，未启用。
- 稠密 KN 布局：多数实际形状更慢；大 lm_head 还出现末位差异，未采用。
- NZ 格式：当前 CANN 的格式转换接口报 500001/编译初始化错误，未修改运行中的 SDK。

尚未证明达到绝对硬件极限。当前稳定配置下，剩余时间主要在设备矩阵计算、
离散 KV 访问和大量小算子执行；上述探针显示直接改布局或用当前 PyPTO 包装
不能保证更快。更低层融合仍需保持参考归约顺序并通过完整模型质量检查。
