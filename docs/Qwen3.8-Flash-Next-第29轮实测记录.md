# Qwen3.8-Flash-Next 第 29 轮实测记录

> 本轮的关键词：**找到模型真正"醒过来"的地方**。
> 上一轮（第 28 轮）的结论是"参考实现自己也一样乱码，所以不是我们的代码问题"。
> **那个结论被本轮推翻了** —— 它只看了 4 层和 8 层，而模型的信号几乎全部在最后 10 层。

## 0. 一句话结论

**模型是真的、这份 checkpoint 是可用的：参考实现（原始 bf16）在 48 层时 mean_nll = 5.4437。
但它在 38 层之前一直是 ~12.4（≈均匀随机），从第 39 层开始才陡降。
所以之前所有在 40 层及以下做的 A/B 全都是"盲测"——那个深度模型本来就还没醒。**

## 1. 怎么做到的：层主序 + 逐层流式

之前的死结：48 层 bf16 要 **336 GB**（`du -sh` 实测，不是估计的 233 GB），
而 <ascend-host> 只有 201 GB 可用内存 → 装不下，所以一直只能用 4 层/8 层做对照。

解法（`tests/t_ref_bf16_depth.py`）：**一次只把一层读进内存**，喂完 T 个 token、
量一次"如果模型到这里结束"的 NLL，再释放该层读下一层。峰值内存只有几 GB。

- **层主序在因果模型里是等价的**：第 i 层第 t 个位置只依赖 ≤t 的位置，
  而第 i 层的全部输入（来自第 i-1 层）在开始处理第 i 层时已经算好。
- 每层用**自己的 DynamicCache** 逐 token 推进，所以 `pos>0` 的路径（KV、QSA indexer、
  DeltaNet 递归状态）全部走真实的参考实现，没有被简化。
- 副产品极有价值：**一次运行就得到 1..48 层的完整 NLL 曲线**。

代价：CPU 上约 **26 s/层**，48 层共 **1282.9 s（21.4 分钟）**。

## 4. 现在的问题变成：我们的 48 层为什么拿不到 5.44？

我们 48 层（QP 权重、kernel 模式、G=32）= **12.5084**，参考 bf16 48 层 = **5.4437**，
差 **7.06 nats**。而 4 层只差 0.015 nats、8 层只差 0.005 nats。

两种可能，必须用一次实验分开：

| 可能 | 预测 |
|---|---|
| A. **我们的推理代码在深层有 bug** | 参考实现 + **同样的 QP 权重** → 也应该拿到 ~5.4 |
| B. **W4/int8 量化在深层是致命的** | 参考实现 + **同样的 QP 权重** → 也会掉到 ~12.5 |

正在跑的就是 A/B 的这一刀：`tests/t_ref_qp48.py`
（参考实现 + 从 QP 反量化的权重，逐层流式 48 层，CPU）。
之所以它也能跑得动：QP 形式只要 2.6 GB/层，逐层反量化、逐层释放。

### 4.1 为什么"量化在深层致命"这个猜测是合理的

模型在 48 层时的预测已经很尖（NLL 5.44 → 目标 token 概率 ≈ 4.3e-3，
而均匀是 4.0e-6，相差 1000 倍）。前面测过**每层的输出相对误差 1.8–2.4%**，
这种量级的扰动在 48 层链式传播后，**足以把那个 1000 倍的 margin 抹平**。
而浅层（仍接近均匀时）完全看不出影响——这正是 §3 表格里那些"无差"的原因。

## 8. 定位过程：三种驱动方式对比（`tests/t_pipeline_diff.py`）

用**同一套 `E.FnLayer`、同一批权重**，只换驱动方式，比 logits：
A=层主序（脚本直调）、B=token 主序 eager（`m.step` 走 `body0/body1`）、C=token 主序 + 图捕获。

| 配置 | A vs B | A vs **C** |
|---|---|---|
| NL=8 单卡 | 0.000% | **0.000%** |
| NL=16 单卡 | 0.000% | **0.000%** |
| NL=16 **跨卡 8+8** | 0.000% | **54.169%** |

**只有"跨卡 + 图捕获"这一种组合是错的。** 而且 C 的 NLL 恰好等于"只跑 8 层"的值
（11.9705）—— 说明 **dev1 那半边在 replay 时根本没生效**。

试过但**无效**的三个修法（都实测过，记下来免得再试）：
1. 整个 step 跑在捕获用的旁路 stream 上 → 反而更差（126.8%）；
2. 中转拷贝后加 `torch.npu.synchronize(h1.device)` → 数值一字不变（不是竞态）；
3. `g1` 在 `torch.npu.device(dev1)` 上下文里捕获+重放、replay 后再同步 → 仍然 54.169%。

结论：**dav-c220 上 `NPUGraph` 跨设备段（dev1 的 24 层）无法被正确捕获/重放**，
这不是加同步能解决的。

## 10. 代价：eager 慢 9 倍

| 配置 | 稳态 |
|---|---|
| 图捕获（错的，但快） | 57.2 ms/token |
| **全 eager（对的）** | **530.96 ms/token** |

三点法：8 token 27.056 s / 32 token 39.799 s → 斜率 530.96 ms/token。

所以现在是一个明确的取舍：**要正确就必须放弃跨卡图捕获**。下一步要把"又对又快"拿回来：

1. **把 48 层全放在一张卡**（`FNX_LPC=48 FNX_NLAYERS=48`）→ 没有跨卡段，图捕获应当可用。
   但这需要显存：46 层 kernel OFF 已 57.26 GiB/卡，48 层单卡要 ~120 GiB → **不可能**。
   除非用 kernel 模式（1.39 GiB/层 → 48 层 67 GiB）→ 也超 64 GiB。**所以要减层或减精度**。
2. **只捕获 dev0 那半边**（`g0` 单卡捕获是好的，实测 0.000%），dev1 那半边走 eager。
   预期能拿回一部分（约 50% 的层可入图），代价是另一半的启动开销。
   **这是最省事、最可能落地的方案。**
3. 每卡各自一张图 + 显式 `aclrtSynchronizeStream` 串联（需要更底层的 stream 控制）。
4. 换用 `torch.npu.graph` 以外的方式：把每卡 24 层编译成一个更长的 kernel 序列（工作量最大）。

### 11.4 想再快，只剩两条路

1. **让模型不跨卡**：把层全放一张卡。46 层 kernel OFF 已 57.26 GiB，48 层 raq 单卡要 ~120 GiB，
   不可能；kernel 模式 1.39 GiB/层 × 48 = 67 GiB 也超 64 GiB。

2. **减少 dev1 的 Python 发射次数**：把 23 层里的小算子手工融合（目前每层约 90+ 个 launch）。

> 另外记一个**方法学教训**：`tests/t_pipeline_diff.py` 在 16 层 8+8 下报 "A vs C = 54.169%"，
> 但生产路径用同样的 g0-only 捕获却与全 eager 逐位相同。说明那个对照脚本在"跨卡 + capture() 之后"

### 12.1 PLE 到底哪里错了（本轮只查到这一步）

排除项：
- `_ple` 的**数学与权重**：`t_b_layer.py` 第 2 层对拍 PASS（impl 0.124%、量化 2.14%），
  那一测覆盖了 `pl_key/pl_val/pl_nq/pl_nc/pl_conv_w` 的用法；
- `NgramTable.row()` 的分片寻址与反量化（`q8 * repeat(s8, 32)`）读代码是对的；
- `ngram_ids` 的位移与 eos 分段逻辑，逐条对照参考实现的 `_shift_right_ignore_eos`
  与 `NGramEmbedding.forward` 后**语义一致**（`sh = [hist[p], hist[p-1], hist[p-2]]`、
  按最后一个 eos 切段、按 `(ngram-2)*heads_per_ngram` 分块、`xor` 混合、`remainder+offset`）。

**剩下的唯一嫌疑：那份 51 GB 的 ngram 表（`/models/Qwen3.8-Flash-Next-Q/NG*.safetensors`）
本身是否与这份 checkpoint 匹配。** 这一点无法在本地用"参考实现"验证（参考实现要
`ple.ple_embedding.weight` 是一个完整 nn.Embedding，装载要 51 GB 且格式不同）。

建议的验证办法（下一轮）：随机取 20 个 `gid`，用我们的 `NgramTable.row(gid)` 解码，
与直接从 `NG*.safetensors` 里按 `data_offsets` 手工切出来的同一行逐字节比对
（这一步能确认分片/偏移/反量化没写错），再抽查这些行的范数分布是否像训练过的 embedding
（如果整表是随机初始化，范数会异常整齐且 PLE 必然有害）。

| 子块 | ms/步 | 占比 |
|---|---|---|
| gated_residual(attn) | 2.19 | 16% |
| **attention (_deltanet)** | **4.62** | 33% |
| inject(attn) | 0.24 | 2% |
| gated_residual(mlp) | 2.17 | 16% |
| **MoE** | **4.21** | 30% |
| inject(mlp) | 0.24 | 2% |

三块（gated_res×2 / attn / moe）各占约 1/3 —— **说明不是某一处特别慢，而是"每层约 90 个 launch"整体摊出来的开销**。
所以 ② 的正确目标是**减少 launch 次数**，不是优化某个算子。

### 14.3 试过的大招：dev1 逐层建图（失败，但值得记）

既然整段 body1 的图跨设备无效，就试**每层一张单设备图**（层间靠固定缓冲区 `self.h1` 串联）：

```python
with torch.npu.device(self.dev1):
    s1 = torch.npu.Stream()
    for L in self.layers1:
        g = torch.npu.NPUGraph()
        with torch.npu.stream(s1), torch.npu.graph(g, capture_error_mode="relaxed"):
            self.h1.copy_(L.forward(self.h1, self.pos1))
```

实测（8 层 4+4，`tests/t_perlayer_check.py`）：

| | ms/step | logits 相对差 |
|---|---|---|
| eager | 91.86 | — |
| **逐层图** | **16.43（5.59×）** | **65.01% ❌** |

**快 5.6 倍但结果不对。** 试过把 replay 从旁路流改到默认流（怀疑和之前一样是中转/流顺序问题）——
数值**一字不变**（还是 65.0146%），说明是确定性的语义差异，不是竞态。

→ **结论：dav-c220 上 dev1 的内核无论如何都无法通过 NPUGraph 正确重放**（整段、逐层、旁路流、
默认流、设备上下文，五种组合都试过）。这条路封死。

### 14.4 剩下的可行提速路线（按性价比）

1. **算子融合（安全，收益可预期）**：把每层 ~90 个 launch 压到 ~30 个。
   重点在三块：
   - `gated_residual`：`rms_norm` 的 4–5 个元素级算子合成一个自定义 kernel；
     `sig/mul/mean` 也可合成；
   - `_moe`：`gather_deq` + `weighted_sum` 目前是 10 个左右的小算子；
   - `_deltanet`：conv 的 `lin + reshape + 补零 + sum` 可以合。
   预期：343 → 150 ms 量级（launch 数减 2/3 对应时间近似线性）。
2. **把 head 的 device 部分也入图**：现在 `head()` 每步 6.52 ms，其中 `lm_head` 是 16 个 chunk
   的反量化+matmul。`mixer + lm_head` 全在 dev0 上 → 可以像 g0 一样捕获（现有代码里有
   `if self.with_head and False:` 的占位，就是为这个留的）。预期省 5 ms 左右。
3. **减少层数**：46 → 40 层（dev1 从 22 减到 17）约省 60 ms，但质量会掉。
4. **换更大显存的卡**：单卡能装 46 层（kernel 模式 1.39 GiB/层 × 46 = 64 GiB 仍然吃紧）
   → 若有一张 96 GiB 的卡，整模型单卡 + 全捕获，直接回到 ~57 ms。
   （用户那台 RTX PRO 6000 有 95.6 GiB，但它是 NVIDIA、且环境装不上，见 §5。）

## 16. ★★ head 入图：能省 0.84 ms，但**破坏正确性**（已回退）

`head()` 里 `mixer + lm_head` 全在 dev0，看起来和 g0 一样可以捕获。
现有代码里本来就有 `if self.with_head and False:` 的占位，本轮把它实现成 `_head_device()` + `gh`：
`head()` 只保留两次中转拷贝，device 部分走 `gh.replay()`。

### 16.1 收益：0.84 ms/步（远小于预期的 5 ms）

| | head 段 | 每步总计 |
|---|---|---|
| 未入图 | 6.52 ms | 64.15 ms |
| **入图** | **5.68 ms** | 64.25 ms |

原以为 head 的 6.52 ms 是 lm_head 的 16 个 chunk 反量化在烧，**实际不是**：
那一段里主要是 `self.h_host.copy_(self.h1)` 这个 **dev1→host 的 D2H**，

lm_head 的真算力只有约 0.84 ms。

### 16.2 正确性：直接崩掉

| 指标 | 未入图 | **head 入图** |
|---|---|---|
| mean_nll(200) | 3.1797 | **12.6094** |
| top1 | 48.00% | 0.50% |
| 输出 | 连贯中文 | `Fixed スポンサーサイトodate_domagd **■Ặ全文...` |

→ 已把 `FNX_GRAPH_HEAD` **默认改回 0**，线上恢复 3.1797 / top1 48% / 343.33 ms。

### 16.3 一条已经很清楚的原则

| 捕获对象 | 结果 |
|---|---|
| dev0 的 `body0`（23 层） | ✅ 正确（层主序 vs 图 replay 逐位一致，实测 0.000%） |
| dev1 的整段 `body1` | ❌ 重放无效（输出退化成只跑 dev0 半边） |
| dev1 的**逐层**图 | ❌ 快 5.59× 但 logits 差 65.01% |
| `head` 的 mixer+lm_head（dev0） | ❌ 省 0.84 ms 但质量崩到 12.61 |

**结论：在这块卡 + 这套 CANN 上，NPUGraph 只有"dev0 上的连续多层"这一种用法是可靠的。**
所有其它位置（跨设备、逐层、含 lm_head 的 QW 分块反量化）都会给出确定性的错误结果
（不是竞态——同一组合重复测出的数值一字不变）。

### 16.4 ② 剩下的唯一安全路线：算子融合

因为剖面显示单层 12.19 ms 平摊在 `gated_residual×2 / attn / moe` 三块（各约 1/3），
且捕获版同层只要 2.05 ms，所以瓶颈就是 **launch 次数**（每层约 90 个）。
融合的优先顺序（按 launch 数）：

| 位置 | 现状 launch 数 | 可融合成 |
|---|---|---|
| `gated_residual` 的 `rms_norm`（每层 2 次） | 4–5 个元素级算子 | 1 个自定义 kernel |
| `gated_residual` 的 `sigmoid/mul/mean` | 3–4 个 | 1 个 |
| `_moe` 的 `gather_deq` | 约 10 个（index_select/cast/mask/reshape/mul） | 3–4 个 |
| `_deltanet` 的 conv（`lin + reshape + 补零 + sum`） | 4–5 个 | 1–2 个 |

预期：launch 数 90 → 30，343 ms → ~150 ms 量级。这是纯 AscendC/torch 算子级工作，
不涉及图捕获，风险可控但工作量明显大于本轮做的这些验证。

> 另一条更快的路（如果有硬件条件）：把整模型放到**单卡 ≥96 GiB** 上，全部捕获 → 直接 ~57 ms。
> 用户那台 RTX PRO 6000 有 95.6 GiB 但它是 NVIDIA、且环境装不上（见 §5）。

## 17. 算子融合第一刀：`rms_norm` 换成 `torch_npu.npu_rms_norm`

### 17.1 做了什么

`engine.rms_norm` 原来约 10 个 launch（`float` / `pow` / `mean` / `add` / `rsqrt` / `mul` /
`+1` / `float(w)` / `mul` / `type_as`），每层调用 2 次。改用 torch_npu 的融合算子：

```python
xf = x.float()
if gs is None:
    out, _ = torch_npu.npu_rms_norm(xf, gamma=(1+w), EPS)      # 1 个融合 kernel
else:
    xg = xf.view(..., -1, gs)
    out, _ = torch_npu.npu_rms_norm(xg, gamma=ones(gs), EPS)   # 分组归一化
    out = out.flatten(-2) * (1+w)
```

`(1+w)` 与 `ones` 都按张量地址缓存（权重常驻，只算一次）。开关 `FNX_FUSED_RMS`（默认 1，
异常自动退回旧实现）。

### 17.2 ★ 一个必须记住的精度陷阱

**第一版直接把 bf16 的 `x` 喂进融合算子、并把 `(1+w)` 折进 gamma → QSA 层对拍从
0.024% 退化到 1.857%（75 倍）。** 原因是 `npu_rms_norm` 对 bf16 输入的内部计算精度不够，
而原实现在 fp32 里算。

修法：**先 `x.float()` 再进融合算子**。实测 fp32 输入下融合算子与原实现**逐位一致**
（rel 0.0000%）。改完单层对拍完全恢复：

| 层 | 未融合 | 融合（fp32 入口） |
|---|---|---|
| L0 linear | 0.116% / 0.157% | **0.116% / 0.157%** |
| L3 full/QSA | 0.024% / 0.023% | **0.024% / 0.023%** |

### 17.3 收益：只有 2.5%（远低于预期）

| | 单次调用（孤立） | 单层 | 46 层 TPOT |
|---|---|---|---|
| 未融合 | 307.5 µs | 12.456 ms | 343.25 ms |
| **融合** | **187.9 µs（1.64×）** | **12.284 ms（1.4%）** | **334.67 ms（−2.5%）** |

质量基本不变：`cap=200` 3.1797 → **3.1862**、`top1` 48%（`cap=3` 9.63 → 9.79，n=3 噪声大）。

**为什么孤立测快 1.64×、层内只快 1.4%？** 说明这层的耗时不是"算子本身"，而是
**device 排队 + 每次 launch 的固定开销**；孤立计时里那部分 Python 开销本来就被摊掉了。

### 17.4 ② 的最终判断（重要）

按这个实测斜率外推：**把每层 90 个 launch 里能融合的都融合（乐观 1/3），
343 ms 大概只能到 300 ms 量级，到不了 150 ms，更到不了 57 ms。**

所以 ② 的结论是：

> **在这套硬件/软件栈上，dev1 那半边的 6 倍差距不是"算子没融合"造成的，
> 而是"没有图"造成的。** 算子融合最多拿回几个百分点；
> 真正的杠杆只有两个：**拿到可用的图捕获**（本平台已证否）或**换一张装得下的卡**。

这轮仍把 `rms_norm` 融合留在代码里（无损、白拿 2.5%），但**不再继续做逐算子融合**——
投入产出比已经不成立。要提速，下一步应该去查"为什么 24 层放不进一张卡"（量化/层数/精度重排），
或者去推进 Cube/op 包那条线，而不是继续削 launch。

## 18. 单卡/混合布点实验：速度换质量的真实曲线

### 18.1 单卡到底能装几层（实测）

| 配置 | 结果 |
|---|---|
| 单卡 46 层（kernel, G=32） | ❌ OOM（torch 可用只有 **60.96 GiB**，稳态需 46×1.40 = 64.4 GiB） |
| 单卡 42 层 | ❌ OOM（装到第 41 层时 57.87 GiB，再要 1.56 GiB 装不下） |
| **单卡 40 层** | ✅ 装下，`npu-smi 62769/65536 MB`，**全部 40 层入图** |

实测单层稳态 **1.40 GiB**（kernel ON / G=32）。同时释放了一处显存浪费：
kernel 模式下 `self.s` 和 `self.s4t` 是同一份 scale 的两份拷贝，现在 `self.s/base = None`。

### 18.2 三种布点的速度/质量实测（同一 `/fnx/loss` 口径）

| 配置 | 捕获层数 | mean_nll(200) | top1 | 稳态 TPOT |
|---|---|---|---|---|
| **2 卡 23+23，torch 路径（现线上）** | 23（g0） | **3.1862** | **48.00%** | **324.17 ms** |
| 2 卡 40+6，kernel 路径 | 40（g0） | 7.6815 | 11.00% | **185.92 ms** |
| 单卡 40 层，kernel 路径 | 40（全） | 10.5575 | 8.50% | **118.83 ms** |

### 18.3 两个重要结论

**(1) 单卡 40 层的质量差不是 bug，是"层数不够"。**
我们单卡 40 层 = 10.5575，参考实现的 depth-40 = 10.4113（§2 那条曲线）——**两者吻合**。
说明捕获是正确的，只是这个模型在 40 层时确实还没"醒"（信号集中在 44–48 层）。

**(2) ★kernel 路径在深层会显著伤质量（单层 0.35% → 46 层 4.5 nats）。**
`40+6` 那个配置里 **46 层一个不少**，唯一变化是"用 kernel 路径 + G=32 换显存"，
结果 mean_nll 从 3.1862 掉到 7.6815。而单层对拍（`t_base_scale.py`）只显示 0.347%/0.356%。

> 这条推翻了一个旧结论：**"kernel 与 torch 路径数值等价（0.35%）"只在单层成立。**
> 模型在 46 层时预测很尖（NLL 3.19），0.35% 的逐层扰动累积 46 次就吃掉 4.5 nats。
> 以后凡是要跑满深度，**必须用 torch 路径**；kernel 路径只能当"省显存换质量"的备选。

### 18.4 于是形成一个硬约束

| 想要 | 代价 |
|---|---|
| 完整质量（3.19） | 必须 torch 路径 → 2.49 GiB/层 → **只能 2 卡 → dev1 无法入图 → 324 ms** |
| 单卡（可全图） | 必须 kernel 路径 → 质量掉到 7.7–10.6 |
| 两者都要 | 需要**一张能装 46 层 torch 路径的卡**：46 × 2.49 = 114 GiB → 需要 ~128 GiB 单卡 |

**结论：在这套 2×60.96 GiB 的硬件上，"3.19 质量 + 324 ms" 已经接近可行区间的边界。**
要再快，只有三条路（按可行性）：
1. **把 kernel 路径的深层精度修好**（让 0.35% 别累积成 4.5 nats）——最值得做，
   因为修好后就能用 `40+6` 甚至单卡 40 层，直接拿到 186 / 119 ms 且不掉质量；
2. 换大显存单卡；
3. op 包/MIX 那条线。

## 19. ★★ 隔离变量：kernel 路径在**相同布点**下就差 8.6 nats

§18 那两组（3.1862 vs 7.6815）一次改了两个变量（**路径** + **布点 23/23 → 40/6**）。
所以先补一组 `kernel + G=32 + 23/23`，把布点固定住：

| 配置（全部 46 层、PLE 关、仅 dev0 入图） | mean_nll(200) | top1 | TPOT |
|---|---|---|---|
| torch 路径 + G=64，**23/23** | **3.1862** | **48.00%** | 318–324 ms |
| **kernel 路径 + G=32，23/23** | **11.8190** | 0.50% | 335.88 ms |
| kernel 路径 + G=32，**40/6** | 7.6815 | 11.00% | 185.92 ms |

**同一布点下，kernel 路径比 torch 路径差 8.6 nats。**
这不是"0.35% 逐层累积"能解释的（那样应该是 4–5 nats 量级、且随层数平滑变化）。

### 19.1 一个反直觉的异常（重要线索）

kernel 路径在 **40/6**（7.6815）反而比 **23/23**（11.8190）**更好**。
两次都是 46 层、同一套权重、同一个 kernel，只有"哪些层在卡0/卡1"不同。

> 这说明 kernel 路径的退化**不是均匀的**，而是**和具体层/布点有关** —— 更像某几层踩到了
> 某个数值边界（例如某层专家 scale 的 fp16 表示溢出、或某层 `s4t` 的极小值趋零），
> 而不是全模型一致的精度损失。

### 19.2 下一步的具体查法（已经想清楚，成本很低）

我们这一侧在 NPU 上很快，所以可以直接**逐层对拍两条路径的 NLL-深度曲线**：

```
OD_NL=46，两次运行：FNX_MOE_KERNEL=0 与 =1
```
用 `tests/t_our_depth.py`（层主序、每层独立状态、2 分钟跑完 48 层），
把两条曲线按深度相减 —— **偏差突然跳起来的那一层就是嫌疑人**。
定位到层之后，再看那几层专家的 `s4t`（fp16）范围，确认是不是溢出/下溢。

|---|---|
| 质量 3.19（可用文本） | ✅ 只有 torch 路径能给 |
| 速度 | torch 路径下 **318–324 ms** 是本机可行边界（dev1 无法入图） |
| 更快的 186 / 119 ms | 需要 kernel 路径 → 质量掉到 7.7 / 10.6 |
| 两者兼得 | 需要先**修好 kernel 路径的深层退化**（§19.2 的查法），或换 ≥128 GiB 单卡 |

## 20. ★★★ H2D 重测：**mmap/分层驻留其实成立**（推翻第 12 轮"不可行"的结论）

### 20.1 为什么旧结论是错的

第 12 轮（`部署方案 §7.9`）测得"专家 gather 只有 3.9 GB/s → offload 不可行"。
那次测的是 **宿主侧 `index_select` 之后再 H2D** —— 慢的不是链路，是**宿主侧随机 gather**。

本轮用 `tools/h2d_bench.py` 重测 6 种模式（每专家 4bit 打包 2.344 MB，每层 top-10 = 23.44 MB）：

| 模式 | 耗时 | 带宽 |
|---|---|---|
| A 连续 23.44 MB，pageable | 1.25 ms | 19.70 GB/s |
| B 连续 23.44 MB，**pinned** | 1.13 ms | **21.78 GB/s** |
| **C 10×2.344 MB 分段 pinned**（每专家一个 blob） | 1.15 ms | **21.37 GB/s** |
| D 宿主 `index_select(10/512)` 再 H2D，pinned | 4.15 ms | **0.74 GB/s** |
| E C 的流水版（一次发完再同步） | 1.15 ms | 21.41 GB/s |
| F 整层 1.48 GiB pinned | 74.51 ms | 21.30 GB/s |

**C 与 D 差 29 倍。** 结论：**只要"每个专家一个连续 pinned blob、不做宿主 gather"，
H2D 就能跑满 21.4 GB/s。** 大块也稳定：`tools/h2d_big.py` 实测 2/8/24 GiB pinned
分别 21.12 / 22.77 / **22.37** GB/s（24 GiB 锁页一次性 34.5 s，root 不受 memlock 限制）。

### 20.2 换算：每 token 流式 K 层的代价（按 21.4 GB/s）

| 流式层数 | 每 token 字节 | 耗时 |
|---|---|---|
| 6 层 | 141 MB | **6.6 ms** |
| 10 层 | 234 MB | 11.0 ms |
| 16 层 | 375 MB | 17.6 ms |
| **23 层**（整张 dev1） | 539 MB | **25.2 ms** |

对照当前 318 ms/token —— **流式 23 层只花 25 ms，完全可接受。**

### 20.3 由此得到一个明确的提速方案

把 dev1 那 23 层的**专家权重放到宿主 pinned（23 × 512 × 2.344 MB ≈ 27.6 GB）**，
让 **46 层全部驻留在 dev0** → **整模型可以对 dev0 做一次完整图捕获**（我们的图捕获只在
单设备下可靠，见 §16.3）。需要新增的只是"每 token 按 expert_id 把 10 个 blob 拷进
设备 workspace"这一步（可双缓冲、与计算重叠）。

粗算：`46 层 × 2.6 ms（捕获态）≈ 120 ms` + `流式 25~36 ms（部分可重叠）` ≈ **130~155 ms**，
对比现在 318 ms → **2.0~2.4×**，而且**不损失质量**（权重还是那份，只是换了驻留位置）。

### 20.4 链路瓶颈在**主机平台**，不在卡（重要）

```
03:00.0  LnkCap: Speed 32GT/s, Width x16   ← 卡本身是 PCIe 5.0 能力件
         LnkSta: Speed 16GT/s (downgraded)  ← 实际只跑 Gen4
83:00.0  同上
```

鲲鹏 920 平台只支持 PCIe 4.0。实测 21.4–22.4 GB/s 已达 **Gen4 x16 有效带宽（25 GB/s）的 86–90%**，
**Gen4 上已无余量**；换到 PCIe 5.0 平台理论上可到 ~42 GB/s（约 2×），**而不用换 NPU 卡**。

但要说清楚：**2× H2D 对当前 318 ms 帮助很小**（流式只占 25 ms，翻倍也只省 12 ms）。
换平台的真正价值是让 §20.3 那个 offload 方案的余量更宽，而不是直接提速。

## 21. ★★ offload 机制落地：逐位一致，2.35 GiB/层 换 1.96 ms/层

### 21.1 实现（`engine.ExpQ.to_host_offload()` + `_staging()`）

- 专家权重（int8 容器 `[E,N,K]`）搬到**宿主锁页**（`pin_memory()`），设备侧释放；
- 所有 offload 层**共享一块设备暂存区** `[10,N,K]` int8（49 MB；每层一块要 1.08 GiB，共享太省了）；
- 每 token 按路由结果做 **10 次连续 H2D**（`staging[j].copy_(q_off[e])`）——就是实测 21.4 GB/s 的那个模式，
  **绝不在宿主做 `index_select`**（那个只有 0.74 GB/s）；
- 开关：`FNX_OFFLOAD_FROM=<层号>`（默认 999 = 关）。

### 21.2 实测（8 层全在 dev0，offload 第 4 层起）

| | hbm0 | 每步 | mean_nll |
|---|---|---|---|
| A 不 offload | 20.33 GiB | 61.48 ms | 12.0915 |
| **B offload 4 层** | **10.96 GiB** | 69.30 ms | **12.0915** |

- **省 9.4 GiB = 2.35 GiB/层**（与预测的 2.34 GiB 完全吻合）；
- **logits 相对差 0.000000%、max 0.000e+00、argmax 全同 → 逐位完全一致** ✅
- 代价 **+1.96 ms/层**（49 MB ÷ 21.4 GB/s = 2.3 ms，吻合）。

### 21.3 ★ 但按这个账，offload 单独用是**亏的**

因为 offload 层的 MoE 必须 eager（H2D 源地址依赖路由结果，不能被图捕获）：

| 配置（torch 路径，单卡 60.96 GiB） | 显存 | 估算时间 |
|---|---|---|
| 现状：dev0 23 层捕获 + dev1 23 层 eager | 57/57 GiB（双卡） | **318 ms** |
| 单卡 24 层捕获 + 22 层 offload（eager 14.3 ms） | ~58 GiB | 62 + 315 = **377 ms** ❌ |
| **单卡 40 层捕获 + 6 层 offload**（需打包 4bit 存储） | ~59 GiB | 104 + 80 = **~184 ms** ✅ |

**结论：offload 只有在"单卡能装到 ~40 层"时才有价值 —— 而那需要打包 4bit 存储
（1.48 GiB/层 vs 现在 int8 容器的 2.49 GiB/层）。**

### 21.4 下一个要做的：打包存储的正确解包（v2 布局自带便利）

我们已经有 kernel 用的 **v2 打包布局**，它的映射是
`byte(64s+j): lo = W[128s + j]`、`hi = W[128s + 64 + j]`。
这意味着解包**不需要交织**，只要两次连续切片赋值：

```python
S = K // 128
b  = qv2.view(k, N, S, 64)
w  = torch.empty(k, N, S, 2, 64, dtype=torch.bfloat16, device=dev)
w[..., 0, :] = (b & 0x0F).to(torch.bfloat16) << 3 ...   # 按 (n^8)-8 还原符号
w[..., 1, :] = (b >> 4)
w  = w.reshape(k, N, K)      # k 索引 = 128s + 64*half + j，正好是 v2 的定义
```

**没有步长 2 交织、没有 `torch.stack`** —— 这正是当初 `FNX_PACK=1` 慢死的原因被绕开的地方。
做完这一步，torch 路径的显存就从 2.49 → 1.48 GiB/层，单卡 40 层成立，
再接上 `FNX_OFFLOAD_FROM=40` 即可实现 §21.3 那一行（~184 ms，质量 3.19 不变）。

## 22. ★★★ 打包存储这条路：**NPU 上整数位运算慢 20–500 倍**，方案要改写成 bf16 算术

### 22.1 v2 布局"块状解包"实测：数值无损，但慢 225 倍

我原本以为 v2 布局（`byte(64s+j): lo=W[128s+j]`、`hi=W[128s+64+j]`）可以靠
"两次连续切片赋值 + reshape"避开交织。实测（`tools/check_pack_unpack.py`）：

| | gate_up | down |
|---|---|---|
| 数值 | **rel 0.000000%、max 0.000e+00（逐位无损）** | 同 |
| 容器解包 | 0.285 ms | 0.173 ms |
| **v2 块状解包** | **63.592 ms（225×）** | **33.524 ms（194×）** |

### 22.2 定位：慢的不是交织，是**整数位运算**

`tools/check_unpack_ops.py` 逐算子计时（[10,1280,1280] uint8 = 16.4M 元素）：

| 算子 | 耗时 |
|---|---|
| `uint8 → bf16` cast | 0.034 ms |
| `uint8 → int16` cast | 0.030 ms |
| `uint8 & 0x0F` | 0.616 ms |
| **`uint8 >> 4`** | **7.313 ms** |
| **`int16 ^8 -8`** | **18.170 ms** |
| **`int16 → bf16`** | 12.877 ms |
| `copy_` 同尺寸 | 0.014 ms |

**结论：NPU 上 uint8 移位、int16 位运算/转换都是慢路径（7–18 ms），而 bf16 算术是快的
（0.03–0.09 ms/op）。** 这就是第 26 轮 `FNX_PACK=1` 慢死、以及本轮两次尝试失败的共同根因 ——
**不是"交织"的问题，是"用了整数位运算"的问题。**

### 22.3 方案 B：在 bf16 算术里解包（`tools/check_unpack_bf16.py`）

```python
pb  = p.to(torch.bfloat16)                 # 0..255，bf16 8 位尾数精确
hi  = torch.floor(pb * 0.0625)             # floor(byte/16)
lo  = pb - hi * 16.0
lo  = torch.remainder(lo + 8.0, 16.0) - 8.0   # (n ^ 8) - 8 的算术等价
hi  = torch.remainder(hi + 8.0, 16.0) - 8.0
# 然后各自乘 scale（组 2s / 2s+1）→ 两个连续 [k,N,K/2]
```

数值与容器路径一致（rel 0.163%，就是 bf16 噪声级）。代价：

| | 容器路径 | bf16 两半 | 差 |
|---|---|---|---|
| gate_up | 解包 0.284 + gemm 0.040 = **0.324 ms** | 解包 1.187 + gemm 0.105 = **1.292 ms** | **+0.97 ms** |
| down | 0.178 + 0.039 = **0.217 ms** | 0.605 + 0.104 = **0.709 ms** | **+0.49 ms** |
| **每层合计** | 0.54 ms | **2.00 ms** | **+1.46 ms/层** |

### 22.4 重算账：打包存储只值 1.3×，不是 1.7×

| 配置 | 显存 | 估算时间 | 质量 |
|---|---|---|---|
| 现状（2 卡 23 捕获 + 23 eager，int8） | 57/57 GiB | **318 ms** | 3.19 |
| 打包后：dev0 40 层捕获 + dev1 6 层 eager | 59 / 8 GiB | 40×4.06 + 6×13.8 ≈ **245 ms** | 3.19 |
| 打包 + offload 6 层（全部 46 层在 dev0） | 59 GiB 单卡 | 40×4.06 + 6×14.9 ≈ **252 ms** | 3.19 |

**打包把"单卡能装 24 层"提到"40 层"，但解包本身每层要多花 1.46 ms，最后只拿到 1.3×。**

### 22.5 修正后的判断

我上一轮估的 184 ms 忽略了**解包代价**，是错的。按实测重算：
**打包存储 ≈ 318 → 245 ms（1.3×）**，工程量不小、收益有限。

真正值钱的两条没变：
1. **移植到 PRO 6000 单卡**（没有跨卡问题 → 全量图捕获 + int8 容器也能装 46 层？—— 95.6 GiB < 114 GiB，
   仍需打包；但单卡 + 打包 = 68 GiB，装得下，且**解包在 CUDA 上是快的**（NVIDIA 的整数位运算不慢）→ 那里
   v2 交织解包可能只要 0.3 ms！这是 PRO 6000 的又一个理由）；
2. **修 kernel 路径的深层精度**（它本来就是打包的、解包在 AscendC 里是 0.3–0.6 ms）。

### 22.6 一条可以复用的硬知识（已值得进 skills）

> **在 910B4 上，uint8/int16 的位运算与整型→浮点转换是慢路径（7–18 ms / 16.4M 元素），
> bf16 算术才是快路径（0.03–0.09 ms）。任何"解包/位操作"都必须先转 bf16 再算。**

这条同时解释了历史上两次失败的 `FNX_PACK` 尝试。

## 23. ★★★★★ 最终判定：**dev1 上的 NPUGraph 完全不可用**（连平凡链都不行）

之前 5 种组合失败都混在"双卡 + 层 + 中转"的复杂实验里，无法排除是别的因素。
`tests/t_dev1_capture.py` 把它拆成梯子，每级只变一处，每级都做 eager vs replay 的数值对比：

| 级别 | 内容 | mode | 结果 |
|---|---|---|---|
| **R4 对照** | 平凡链 `out = x*2+1`，**dev0** | relaxed | **rel 0.0000% → PASS ✅** |
| R1 | 平凡链，dev1，`set_device(1)` | relaxed | **rel 100.0000% → FAIL ❌** |
| R2 | 平凡链，dev1，current_device=0 | relaxed | **rel 100.0000% → FAIL ❌** |
| R3 | 平凡链，dev1 | **global** | **rel 100.0000% → FAIL ❌** |

`rel = 100%` 的物理含义非常干净：**replay 之后输出仍然是全零** —— 图根本没有执行。

**结论（锁死）**：
> 在这块 910B4 + 这套 CANN 上，**NPUGraph 只能在 current_device=0 上捕获与重放**；
> dev1 上的图捕获**连一个两算子链都不工作**，与模型、层、跨卡中转、stream、捕获模式全部无关。

这也反过来说明：**之前那个"两边都捕获 → 57.2 ms"之所以快，是因为 g1 是空转**。
真正的 46 层全捕获在 910 上不可能实现。

## 24. ★★★★★ 打包存储落地：**318 → 168.5 ms，质量不变**（1.89×）

### 24.1 实现要点（三个真问题，全部实测踩过）

1. **解包必须在 bf16 算术里做**（§22）：`uint8>>4` 7.3 ms、`int16^8-8` 18.2 ms，
   而 bf16 算术 0.03–0.09 ms/算子；
2. **不能物化交织权重**（块状跨步写 63.6 ms）：改成解出 **lo/hi 两个连续数组**，
   下游做**两次 GEMM**，把"取奇偶"的切片挪到**激活**上（[10,1,K]，几十 KB）——
   `_split_halves()` + `_gemm2()`；
3. **int8 容器不能进显存**（这一条是装不下 40 层的真凶）：打包时若让设备同时持有

   （`allocated 49.19 GiB, reserved 59.52 GiB, free 1.08`）。

## 25. ★★★★★ LQP artifact 落地：冷启动 **818 → 46 s**，TPOT **168.5 → 125.3 ms**
