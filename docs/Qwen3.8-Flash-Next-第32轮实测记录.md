# Qwen3.8-Flash-Next 第 32 轮实测记录

> 本轮目标：**提高推理速度**。
> 结果：TPOT **139.5 → 121.1 ms（−13.2%，7.2 → 8.3 tok/s）**，`mean_nll` 保持 **2.1756** 不变。
> 做法只有一个关键词：**装载期预反量化**（把"每 token 重做一遍"的 int8→bf16 反量化改成装载期一次做完）。

---

## 0. 一句话结论

| 项 | 前 | 后 | 变化 |
|---|---|---|---|
| TPOT（96 token 输出） | 139.5 ms | **121.1 ms** | **−13.2%** |
| 吞吐 | 7.2 tok/s | **8.3 tok/s** | +15% |
| TTFT（热态） | 0.16 s | **0.14 s** | −12% |
| `mean_nll`（200 token） | 2.1756 | **2.1756** | 0（逐位相同） |
| 配置 | LPC=46 | **LPC=45 + 三级预反量化** | — |
| 冷启动 | 30 s | 31 s | +1 s（前缀缓存提前构建） |

## 1. 为什么这个优化管用

第 30 轮 §16 量到：**每 token 的最大开销是"把整层 int8 权重重新反量化一遍"**。
`tests/t_batch_micro.py` 进一步给出关键事实：

| | 耗时 |
|---|---|
| int8 权重 `E.lin(x, W)`（含反量化） | **0.20 ms** |
| 同一块权重的纯 bf16 matmul | 0.04 ms |
| 同一个 int8 权重、B=1 / B=8 / B=32 | 0.20 / 0.19 / 0.19 ms |

⇒ 成本的 80% 是**反量化这一次固定动作**，与 batch、与矩阵形状几乎无关。
既然权重在显存里是常驻的，那就**在装载期反量化一次、之后直接 GEMM**：

- 数值上**逐位相同**（反量化本来就是 `q * scale`，只是不再每 token 重算）；
- 代价是显存：bf16 比 int8 大一倍。

## 2. 三级预反量化（三个 flag，可单独开关）

| flag | 对象 | 每层字节 | 实测收益 | 显存代价 |
|---|---|---|---|---|
| `FNX_DEQ_SMALL=1` | 每层 11 个小权重（`a_down/a_up/m_down/m_up/a_inj/m_inj/sh_gate/sh_up/sh_down/sh_gate2/gate_w`） | 19.8 MiB int8 → 39.6 MiB bf16 | **−15.6 ms（−10.8%）** | +10 MiB/层 |
| `FNX_DEQ_HEAD=1` | `lm_head`（606 MiB int8，原来分 16 块每 token 重反量化） | 606 MiB → 1.18 GiB | **−5.5 ms（−3.9%）** | +0.6 GiB（放 dev1，那里空） |
| `FNX_DEQ_ATTN=10` | 前 10 层的注意力投影（`w_qkv/w_z/w_out` 等） | 55 MiB int8 → 110 MiB bf16 | **−7.2 ms（每层 0.72 ms）** | +55 MiB/层 |

**最反直觉的一行是第一行**：11 个小权重只占稠密字节的 **26%**，却贡献了 **10.8% 的总加速** ——
因为它们单个都太小，反量化开销与权重尺寸无关，所以"越小越亏"。

## 3. 为什么最后是 LPC=45 而不是 46

预反量化要吃显存（小权重 +10 MiB/层、注意力 +55 MiB/层），而 dev0 在 LPC=46 时只剩 ~0.5 GiB。
于是有一个明确的取舍：

| 方案 | TPOT | 说明 |
|---|---|---|
| LPC=46 + 小权重 + head（无 attn） | OOM | 差 24 MB |
| LPC=46 + head（无小权重/attn） | 135.9 ms | 只吃 head 的收益 |
| **LPC=45 + 小权重 + head + attn=10** | **121.1 ms** | ✅ 定稿 |
| LPC=45 + 小权重 + head（attn=0） | 129.4 ms | |
| LPC=44 + 小权重 + head + attn=32 | 123.3 ms | 多丢一层捕获，反而不划算 |

**结论：少捕 1 层（代价 ~12 ms）换来 32 层份的预反量化预算，是这轮最赚的一笔账。**

## 4. 上限在哪：attn=10 之后就是悬崖

- `attn=12`：装配能过、前缀缓存也能建，但**图 replay 直接失败**：
  ```
  RuntimeError: replay ... error code 507899
  Resource_Error_Insufficient_Device_Memory(EL0019): Failed to allocate 33554432 bytes
  ... halStreamTaskFill failed ... Build SQ/CQ failed ... rtModelExecute execution failed
  ```
  图 replay 需要 ~32 MB **驱动侧**内存（SQ/CQ 绑定），torch 的缓存分配器帮不上忙。
- `attn=14`：装配阶段就 OOM（差 62 MB）。
- ⇒ **attn=10 是安全上限**，对应的 dev0 稳态占用 59.57 GiB（reserved 60.41，驱动可用余量 ~0.55 GiB）。

## 5. 顺带修掉的两个真 bug

### 5.1 前缀缓存构建失败会变成"每请求 500"

原先 `_build_prefix` 的异常只在 `Engine.__init__` 里被吞掉，但**没有记录失败**；
`_prefix_hit` 每个请求都会再试一次构建 → 显存贴边时**每个请求都 OOM → 全部 500**
（流式客户端看到的是"空回答"，因为 SSE 里一个 content 都没有）。
修：失败时写入 `([], None)` 哨兵，该模板变体**永久降级为无缓存**，服务继续可用。

### 5.2 前缀缓存应该在建图之前构建

前缀缓存构建要克隆 ~20 MB 状态；放在图捕获之后时，图的池子已经占住显存，贴边就 OOM。
把顺序改成 **装配 → 建前缀缓存（eager 跑 3 个 token）→ 图捕获**，构建成功率明显提高
（attn=12 就能建成；虽然它最终仍因 replay 内存不足而不可用）。
副作用：冷启动 +1 s（eager 跑 3 个 token）。

## 8. 追加：专家 scale 从 g64 减半到 g128（→ 115 ms）

### 8.1 先排除一个诱人的误会

每层专家占 **1.21 GiB**，我一度怀疑它不是真 4-bit（2.517 G 参数 × 0.5 B = 1200.0 MiB，
而实测 `.v2o` 正好 1200.0 MiB）—— **核对结果是：已经是真 4-bit 打包（2 个 nibble/字节），
每参数 0.500 字节，没有任何浪费**。这条路没有 2× 可省。

### 8.2 唯一可压的是 scale

专家 scale 每层 **37.5 MiB**（int8 `s8[E,N,K/64]` + 每行 fp16 `base[E,N]` = 41.3 MiB）。
把组从 64 翻到 128，scale 减半：

| | 每层 scale | 45 层合计 |
|---|---|---|
| g64 | 41.3 MiB | 1.81 GiB |
| **g128** | **22.6 MiB** | **0.99 GiB** |
| 省 | **18.7 MiB/层** | **0.82 GiB** |

**质量代价（先模拟、再真打包，两次独立验证）**：
`mean_nll 2.1756 → 2.1860`（+0.0104）、`top1 49% → 48%`、`median_rank` 仍 1、
**任务级 MCQ 仍 24/24**。teacher-forcing 是确定性的，所以这 +0.01 是真实的（不是噪声），
但幅度只有第 30 轮测得的"量化总代价"的 1/20。

### 8.3 省下的显存花在哪：attn 10 → 20

| 配置 | TPOT | dev0 | mean_nll |
|---|---|---|---|
| g64 + attn=10（r32） | 121.1 ms | 59.57 GiB | 2.1756 |
| g128 + attn=10 | 117.2 ms | 58.69 GiB | 2.1860 |
| **g128 + attn=20** | **115.1 ms** | 59.18 GiB | 2.1860 |
| g128 + attn=26 | 115.8 ms | 59.48 GiB | 2.1860 |

**attn 超过 20 就没有额外收益**（26 反而略慢，且更贴显存边界），所以定稿 attn=20。

### 8.4 实现要点（兼容旧 artifact）

- `_deq_v2` 现在**按 `self.s` 的列数自动识别** g64/g128 两种布局；
- `ExpQ.from_packed` 的 `gs` 从 artifact 推断（不再写死 64）；
- `tools/repack_v2.py` 支持 `FNX_LQP_GS=128`，产物写**新目录**（`-g128`），g64 旧 artifact 保留可回滚；
- 打包耗时 1297 s / 48 层（可续跑）；部署脚本优先用 `-g128` 目录，缺了回落到 `-LQP`。

### 8.5 本轮累计

| | r31（优化前） | r33（本轮后） |
|---|---|---|
| TPOT | 139.5 ms（7.2 tok/s） | **115–119 ms（8.4–8.7 tok/s）** |
| TTFT 热态 | 0.16 s | **0.13–0.14 s** |
| 冷启动 TTFT | ≈0.14 s × token | **≈0.115 s × token** |
| mean_nll | 2.1756 | 2.1860（+0.010） |
| MCQ | 24/24 | 24/24 |

**净提速 −17.5%**，代价 `mean_nll` +0.010、`top1` −1 点。

## 9. 追加评估：专家 3-bit —— 质量可谈，但实现过不去（放弃）

动机：专家权重占每层 1.21 GiB 的 94%，也是 dev0 显存的全部大头。如果能降到 3-bit，
每层省 ~300 MiB、45 层约 **13 GiB** —— 足够把 **48 层全部图捕获**（收回 dev1 那 3 层 eager 的
36 ms）并把**全部层的注意力投影预反量化**（再省 ~25 ms），理论上能把 118 ms 压到 **55–60 ms**。

### 9.1 质量代价（用和 g128 同样的"只改加载"模拟法）

4-bit 每组 16 个电平、步长 `s`；3-bit 在同动态范围下只有 8 个电平、步长 `2s`。
所以把 nibble 值量化到偶数即可**精确模拟 3-bit 的量化误差**（`FNX_SIM_EXP3=1`）：

| 口径 | 4-bit（现役） | 3-bit（模拟） |
|---|---|---|
| `mean_nll`（200 token） | 2.1860 | **2.3793（+0.19）** |
| ppl | 8.90 | 10.80 |
| `top1` | 48.0% | 50.0% |
| 重复英文 NLL | 0.2210 | 0.1942（更好） |
| 24 题 MCQ | 24/24 | **24/24** |

**质量侧结论**：+0.19 nats 是真的退化（deterministic 口径），但比当年"少跑 2 层"的代价（1.01 nats）
小 5 倍，且任务级准确率没掉。单看质量，这张牌不是不能打。

### 9.2 但我放弃了：实现上有硬障碍

要真省内存，3-bit 必须**位打包**（16 个值挤进 6 字节）。而我们的解包链路有一个硬约束：

- 第 29 轮实测：**NPU 上整数位运算极慢** —— `uint8>>4` **7.313 ms**、`int16^8-8` **18.170 ms**
  （16.4M 元素规模），而 bf16 算术只要 **0.03–0.09 ms**；
- 现在 4-bit 能用 bf16 算术解包，纯粹是因为**每字节正好两个 nibble、按 16 进制对齐**
  （`floor(x/16)` 与 `x - 16*hi` 都是精确的 bf16 运算）；
- 3-bit 的值在 24 bit 组里**不按字节对齐**，无法用"除以 2 的幂 + 取余"的 bf16 技巧拆出来，
  只能走移位/掩码 —— 按上面实测的数字，解包这一项就会从 ~2 ms 涨回 60 ms+，把收益全吃掉。

**结论：3-bit 专家在当前 Ascend 910B4 + 纯 torch 算子链路上不可行。**
如果将来要做，前提是有一个**融合的 3-bit GEMV kernel**（解包在 CP/AI Core 内部完成），
而不是在 torch 里解包 —— 那又回到了第 29 轮 kernel 路线的精度问题（同布点 `mean_nll` 差 8.6 nats，未定位）。

### 9.3 那么现在的天花板在哪

118 ms 的构成（第 30 轮拆分 + 本轮预反量化后的估计）：

| 项 | 估计 | 还能怎么收 |
|---|---|---|
| dev1 的 3 层 eager | **~36 ms（31%）** | 需要 3 × 1.29 GiB dev0 显存 —— 与预反量化抢同一块预算，已无空间 |
| MoE（top-10 专家 gather + 解包 + 2 GEMM） | ~55 ms | 只能靠可用的 fused kernel |
| attention（已部分预反量化） | ~25 ms | 剩余 28 层需 1.5 GiB 显存 |

**三条路都卡在同一件事上：dev0 只剩 ~0.9 GiB，而任何一步都需要 GiB 级显存。**
在没有可用 fused kernel 的前提下，115–120 ms（8.5 tok/s）基本就是这套代码 + 这块卡的天花板。

## 10. 追加：AscendC fused kernel 路线 —— 三项证据判定为死路

用户方向：把 MoE 的 gather + 解包 + GEMM 合成一个 AscendC kernel（同时解掉"MoE 55 ms"和"3-bit 不可行"）。

实测三项证据，逐项否决：

### 10.1 精度其实没问题（0.2%）

`tests/t_kernel_feasibility.py` 在真实 L00 权重、bf16 口径下对拍：

| 投影 | N | K | rel_mean | max\|Δ\| |
|---|---|---|---|---|
| `gate_up_proj` | 1280 | 2560 | **0.197%** | 0.0020 |
| `down_proj` | 2560 | 640 | **0.198%** | 0.0009 |

所以第 29 轮那个"同布点 `mean_nll` 差 8.6 nats"**不是单算子精度问题**（0.2% 传不到 8.6 nats），
更像是当时把"kernel 路径（必须运行时打包）"和"LQP artifact 路径"两个变量混在一起比了。

### 10.2 但它和内存优化的 artifact 不兼容

代码事实（本轮核实）：`ExpQ.from_packed` 只设 `qv2`，**从不构造 `s4t`**；
而 `_moe` 的 kernel 分支要 `self.exp_gu.s4t`：

```
from_packed: qv2=(512,1280,1280)  s=(512,1280,20)  gs=128
s4t = None    ← kernel 分支要的就是这个
```

kernel 要的是 **g32 fp16 的转置 scale**（`prepare_layer` 的契约），而 artifact 里是 g128 int8 + base。

### 10.3 把 s4t 造出来要多花 5.6 GiB

| | gate_up | down | 合计/层 | 45 层 |
|---|---|---|---|---|
| s4t（g32 fp16） | 100 MiB | 50 MiB | **150 MiB** | 6.59 GiB |
| 现在的 s8+base（g128） | — | — | 22.6 MiB | 0.99 GiB |

⇒ 每层多 **127 MiB**，45 层多 **5.60 GiB**。而 dev0 只剩 **0.9 GiB**。
要用 kernel 就得放弃约 4 层图捕获（+48 ms/token），而第 29 轮又实测 kernel 进图后**比 torch 慢**
（41.8 vs 26.8 ms，因为 Cube 直调不可用，只能跑 Vector）。

**结论：kernel 路线在"910B4 + 纯 Vector 直调 + 我们的内存布局"这三个约束下不可行。**
这也顺带说明 3-bit 专家没有 kernel 逃生门（见 §9.2）。

## 11. 追加：真正的大鱼 —— dev1 的 eager 路径没切设备上下文（−12 ms）

排查"dev1 那 3 层 eager 为什么这么贵"时发现的：

| 层 | 整层耗时 | `lin()` 调用次数 |
|---|---|---|
| dev0 L00（eager） | **8.11 ms** | 16 |
| dev1 L45（eager） | **13.74 ms** | 16 |

同样 16 次 GEMM，dev1 慢 5.6 ms。原因不是板间差异，而是：

> **`body1()` 和 `_head_device()` 在 dev1 上执行时，`torch.npu.current_device()` 仍然是 0。**
> 每个算子都要做一次设备切换 —— 这是纯粹的上下文缺失，不是计算。

修复（`with torch.npu.device(...)` 包住）：

| | 修前 | 修后 | 省 |
|---|---|---|---|
| dev1 单层 forward | 13.58 ms | **7.85 ms** | −5.74 ms/层 |
| head（dev1） | 8.74 ms | **5.66 ms** | −3.07 ms |
| **整请求 TPOT** | 118.0 ms | **106.0 ms** | **−12.0 ms（−10.2%）** |

`mean_nll / top1 / MCQ` **完全不变**（只加了上下文管理器，没改任何计算）。

## 12. msProf 实测（第 34 轮）：瓶颈是**反量化的逐元素链**，不是 GEMM

采集方式：`torch_npu.profiler`（CPU+NPU，warmup 1 + active 3 步，captured 路径），
导出 `kernel_details.csv` 后按算子聚合 Task Duration。

**总设备时间 265.48 ms / 3 步 = 88.5 ms/step**（同一时刻墙钟约 103–106 ms
⇒ **每 token 有 ~15–17 ms 是宿侧空隙**，不是设备在算）。

| 算子（aclnn） | ms/step | 占比 | 来自哪里 |
|---|---|---|---|
| **Mul**（逐元素乘） | **25.8** | **29.1%** | `_deq_v2` 的 `lo*s_lo`/`hi*s_hi`（2×16.4M/层）；`inject`、`_deltanet` 的若干乘 |
| MatMul | 14.2 | 16.0% | 稠密 GEMM + head |
| **InplaceCopy→Cast（bf16 转换）** | **9.2** | **10.4%** | `pb.to(bf16)`（16.4M/层）、`se/base.to(bf16)`、`xf.to(bf16)` 等 |
| Subs（标量减） | 5.0 | 5.7% | `_deq_v2` 的 `lo-8`/`hi-8`（offset-binary 还原） |
| Sub | 4.3 | 4.9% | `pb - hi*16`、`kc*(1-onehot)` 等 |
| BatchMatMul | 4.2 | 4.8% | `_gemm2` 的两次专家 GEMM |
| IndexSelect（gather） | 3.7 | 4.2% | 专家 slab gather + embedding |
| Muls（标量乘） | 3.4 | 3.8% | `pb*0.0625`、`/math.sqrt` 等 |
| ReduceSum | 2.3 | 2.6% | `(buf*conv_w).sum`、`(S*k).sum`、`(S*q).sum` |
| Transpose | 2.0 | 2.2% | `deq_w` 的 reshape 转置 |
| **Floor** | **1.9** | **2.1%** | `torch.floor(pb*0.0625)`（可合成一步） |
| Matmul_Slice / InplaceCopy_Slice | 1.7 / 1.2 | 3.2% | `deq_w` 的切片 |
| Mean | 1.5 | 1.7% | `gated_residual` / `dn_norm` 的 `mean(-1)` |
| Add | 1.3 | 1.5% | |
| RepeatInterleave | 0.9 | 1.0% | `_deltanet` 的 q/k 复制 |

### 12.1 关键判读：**反量化链 ≈ 51%，GEMM 只占 26%**

把属于"解包 + 反量化"的算子加起来：
`Mul 25.8 + Cast 9.2 + Subs 5.0 + Sub 4.3 + Muls 3.4 + Floor 1.9 ≈ **49.6 ms（56%）**`
（其中 `Sub 4.3` 里有一部分是 attention 的 one-hot 运算）。

真正的矩阵乘（MatMul + BatchMatMul + Transpose + Slice）≈ **23 ms（26%）**。

**这与之前"MoE 55 ms / attention 45 ms / 其它"的消融口径不矛盾，但定位更准**：
MoE 段里真正贵的是**把 10 个专家的 16.4M 个 4-bit 值解包并乘上 scale**，
GEMM 本身很快。也就是说：**这块卡的瓶颈是 Vector 单元的逐元素吞吐，不是 Cube 的矩阵算力。**

### 12.2 由此得到三个具体可动的点

1. **`Floor` + `Muls` 可以合成一步**：`torch.floor(pb * 0.0625)` 现在是"乘 0.0625 → floor"两个 kernel，
   改成 `torch.div(pb, 16, rounding_mode="floor")` 一个 kernel。预计 −1.9 ms（2%）。
2. **`-8`（offset-binary 还原）的两趟 Subs 可以折进 GEMM**：
   `Σ_k (n'-8)·s·x = Σ_k n'·s·x − 8·Σ_k s·x`，后一项是 **[N, K/64] 的 scale 矩阵** 和
   **x 的分组和（[K/64]）之间的小 matvec**（N×40），只有几千个元素。省掉 2×16.4M 的减法，预计 −5 ms。
3. **`Mul`（25.8 ms，最大头）要想省，必须把 scale 折进 GEMM**：
   改成"按 64 组的分组点积"——`A[n,g] = Σ_{k∈g} n'[n,k]·x[k]`（`einsum('ngk,gk->ng')`），
   再 `y[n] = Σ_g s[n,g]·A[n,g]`。这样**不需要物化反量化后的权重**，
   scale 乘法从 16.4M 个元素降到 N×40 个。**预计 −10~15 ms（10–17%）**，
   但需要先基准测一下 NPU 上 `einsum` 带 batch(G=40) 的实际效率 —— 可能被 batch 维拖慢。

### 12.3 还有 15–17 ms 的宿侧空隙

设备 88.5 ms vs 墙钟 103–106 ms。这部分是 Python/调度空隙（每 token 约 30 个 host 侧调用 +
跨卡中转 + `.item()` 同步）。要收它只能靠更少的 host 往返（例如把采样也放进图里，但 dev1 捕获不可用）。

## 13. op 级微基准（`tools/op_bench.py`）：把两个 msProf 候选正式判死

规矩：**任何进热路径的算子替换，先在真实形状上过这个工具**（默认每个候选 5 次，
只占几十 MB 显存，可与线上服务共存；显存紧张时先停服务）。判据：**稳定快 ≥3%** 才值得动生产。

真实形状：`pb/lo = [10, 1280, 1280]`（10 专家 × 1280 行 × K/2），`s = [10, 1280, 20, 1]`

| 候选 | 实测 | 结论 |
|---|---|---|
| `floor(pb * 0.0625)`【生产】 | **0.098 ms** | 基准 |
| `torch.div(pb, 16, rounding_mode="floor")` | **要 252 MiB**（输入只有 32 MB，**8×**）→ 显存紧张时直接 OOM | ❌ **不只是慢，是内存炸点** |
| `torch.floor_divide(pb, 16)` | 同上，252 MiB | ❌ |
| `pb.div(16.0).floor_()` | **0.078 ms（−20%）** | ✅ 唯一真正更快的，但只值 ~0.4 ms/token（0.4%）< 3% 门槛 → **不进生产** |
| `addcmul(-8s, n', s)` | **0.122 ms** vs `mul` 0.084 / `sub` 0.060 | ❌ 比它要替换的两个原语都慢 |

**这就解释了上一轮为什么把生产拖死**：`div(rounding_mode="floor")` 在这块卡上会申请
**8 倍**的临时内存（252 MiB）—— 在一个只剩 0.9 GiB 的服务进程里，这个 op 会把分配器推到
边界反复重试，单个 `/fnx/loss` 从 30 s 变成 >100 s 未完成。`addcmul` 则是纯粹的逐算子慢。

**方法论收获（写进规矩）**：
1. msProf 的"kernel 数"和"墙钟时间"不是一回事 —— 少一个 kernel 可能换来一个 8× 内存的 op；
2. 同形状的 `div`、`fmod`、`floor_divide` 在这块卡上都有 8× 临时内存的问题，**逐元素取整一律用 `mul + floor`**；
3. 广播类算子（`addcmul`）在没有实测前不要当"融合"捷径。

## 14. 最后一个候选也被 op 基准判死：分组点积（scale 折进 GEMM）

思路（msProf §12.2 的第 3 条）：不再物化反量化后的权重，改成
`A[k,n,g] = Σ_{j∈g} lo[k,n,g,j]·x[k,g,j]`，再 `y = Σ_g s[k,n,g]·A[k,n,g]` ——
**scale 乘法从 16.4M 元素降到 k·N·G = 256K**，理论上能省掉那 25.8 ms 的 `Mul`。

`tests/t_grouped_deq.py` 在真实形状（k=10, N=1280, K=2560, G=20×64）上实测：

| 实现 | 耗时 | 相对生产 | 数值差异 |
|---|---|---|---|
| **生产：物化 w + 一次 bmm** | **0.117 ms** | 基准 | — |
| 候选 A：`einsum('kngj,kgj->kng')`（batch=G） | 0.218 ms | **+113%** | rel 0.323% |
| 候选 B：batch=k·G=200 的 `bmm` | 0.179 ms | **+76%** | rel 0.323% |

**结论：更慢。** 这块卡上"批量很小的 matvec"（batch 20 或 200）的效率远低于
"物化 16.4M 元素 + 一次大 bmm"。也就是说：**那 25.8 ms 的 `Mul` 反而买到了 bmm 的高效率**，
把它省掉得不偿失。

## 15. 提速到此为止：四条路全部闭合（都有实测）

| 方向 | 结论 | 关键证据 |
|---|---|---|
| **chunked prefill** | 不做 | 需 ΔNet 分块形式 + grouped MoE，数天工作量、数值要重验（第 30 轮 §16） |
| **多请求 batching** | 机制已就绪，收益不足 | B=2 只有 1.43×，单请求 +38%（第 31 轮 §5） |
| **AscendC fused kernel** | 不可行 | Vector-only 更慢；与 LQP artifact 不兼容；补 s4t 要 5.6 GiB（§10） |
| **专家 3-bit** | 不可行 | 质量 +0.19 nats，但位解包只能走移位/掩码（NPU 上 7–18 ms/16.4M）（§9） |
| **scale 折进 GEMM** | **更慢** | einsum +113% / batched bmm +76%（§14） |
| **算子级替换** | 全部更慢 | `div(rounding_mode)` 要 8× 内存；`addcmul` 慢 34–100%（§13） |

### 15.2 剩余未被证否的唯一方向

**写一个真正融合的 4-bit GEMV kernel，且必须能跑 Cube**（当前直调链路只能跑 Vector，
这是第 29 轮就确认的事实）。如果将来 CANN 版本允许 `bisheng` 直调 Cube，或者能通过
aclnn 自定义算子接口带 Cube，则"解包 + 乘 scale + GEMM"可以真正融成一个 kernel ——
那是唯一能突破 Vector 吞吐墙的路径。**在那之前，105 ms 就是这套代码 + 2×910B4 的天花板。**
