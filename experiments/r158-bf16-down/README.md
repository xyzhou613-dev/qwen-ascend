# r158：BF16 权重舍入的 down 数值修正探针

2026-11-13。本轮没有安装到服务，未构建第二份 Engine，也没有新的性能或整模型质量结论。

r157 组合版实测 8k/长文 TPOT 27.96/28.54ms；完整 100352 目标 NLL 与 10 个新自然文本切片均在门槛内。但旧 natural18000 真 prefill 的 ΔNLL=+0.070638，超过 +0.05；同一切片 W8A8 单独版本为 +0.013832。新增 down 数值路径需要更贴近既有计算。

r156 down 将 INT4×激活先作 FP32 组内规约，再乘 BF16 scale。此探针改为先计算每个 INT4 权重×scale，并舍入为 BF16，再乘激活；其余布局、输入输出 BF16、64 个 K 分组规约、FP32 累加及最终 BF16 舍入保留。用同一个真实 L00 down 权重对象比较原生产 W4A16、旧直接 down 和新变体。不能仅据该代数差异认定已解释所有整模型误差。

使用 1/32 allocator 上限、单个 down 权重，无额外权重重排，53 组输入、四档幅度，覆盖全部 512 专家，并含重复专家 511。数值结果：

| 对生产 down 的比较 | 旧直接 down | 新 BF16 权重舍入 |
|---|---:|---:|
| 最大 relative L2 | 0.002354042 | 0.000099171 |
| 新变体最低逐位相同率 | — | 99.9844% |

新变体 tile64/128/256 的最大 relative L2 相同；tile128/256 在更新输入及专家 ID 后 graph/eager 逐位相同。独立 CPU“先舍入 BF16 权重”公式对新 kernel 的 relative L2≈6.64e-9。峰值张量分配 515901440 字节（约 492 MiB）。这是 L00 组件证据，仍有少量 BF16 差异，可能与 FP32 规约顺序有关；不能宣称与生产逐位等价或精度已经验收。

数值探针与 r157 质量任务共享设备，未作 kernel 时序比较。完整测试的输入、模型源码、质量脚本和检查点未改。源代码及二进制哈希、逐样本误差、内存上限见 numeric-result.json。

首次启动错误地将物理编号 3 用作容器 runtime 掩码，CANN 在初始化阶段报告没有可见设备，探针退出。核实原服务 ASCEND_RT_VISIBLE_DEVICES=0 后重试成功，失败日志保留。该机器节点为 /dev/davinci3、5，runtime 逻辑编号与物理编号不能直接互换。

编译与运行通过独立 systemd unit、容器内 timeout 限时；探针已退出。bf16_weight_down.cpp 由 prepare_variant.py 从 r156 源码生成，variant.patch 可复核。库只导出组件函数 fnx_w4_bf16w，不是旧完整 MoE 库的直接替换品。

下一轮先复验旧 18k 整模型切片，同时独立测真实 down+epilogue 是否仍有收益；之后才做完整层、全量质量与 HTTP 对照。r157 的 18% 输出速度提升不能转记到此数值修正版。正式服务继续使用 r152。
