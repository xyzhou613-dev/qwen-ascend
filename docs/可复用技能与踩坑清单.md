## 1. 工具链技能（Windows 本机 ↔ 两台服务器）

| 场景 | 用什么 | 要点 |
|---|---|---|
| SSH 到 910（`192.168.18.206`，root/kylin@123） | `_work/r206.ps1 -Command '…'` | **直接 `ssh` 会挂住**，必须用这个 SshNet 包装（`backend/remote/rs.ps1` 的简化版） |
| SSH 到 PRO 6000（`192.168.19.201`，server/deepc@123） | `_work/r201.ps1 -Command '…'` | 同上 |
| 上传 GB 级文件 | `backend/remote/rsput.ps1`（SFTP） | 实测 ~110 MB/s；841 MB 数据集、52 GB 权重都靠它 |
| 上传小文件/脚本 | `_work/put206.ps1` | **base64 分片 ≤30 KB**（`rs.ps1` 单包上限约 68 KB）；**分片名必须零填充**，否则 `cat x_*.b64` 会把 `_10` 排在 `_2` 前、文件被拼坏 |
| 下载 | `backend/remote/rsget.ps1` | 取日志、取别人写的文档 |
| 远端长任务 | `docker exec -d fnx bash -lc "… > log 2>&1"` + 轮询日志 | 不要用 SSH 通道等（会超时并把任务挂死）；跑完核对 `logs/*.log` |
| 跨机直传 | `tar cf - -C 源目录 X \| ssh -i ~/.ssh/id_910 root@目标 "tar xf - -C 目标"` | 910 上**没有 rsync**；先 `ssh-keygen` + 把公钥写进目标机 `/root/.ssh/authorized_keys` |
| 发布到 GitHub | 服务器上 `bash /root/ascend-dev/p297_push.sh` | 用 deploy key 推；仓库工作区在 `/root/qwen-ascend` |
| 启停模型 | `/root/ascend-dev/modelctl.sh` | 详见 `docs/910B4-模型启停脚本说明.md` |

**远端执行的三条硬规则**

1. 脚本要放在**宿主机的 bind mount** 里（`/root/ascend-dev/…`），容器内 `/tmp` 与宿主 `/tmp` 不是同一个；
2. 容器里跑 Python 用 `/root/ascend-dev/venv/bin/python`（有 torch/torch_npu/numpy），宿主机 `python3` 只有标准库；
3. 长命令写成 `.sh` 上传后执行，别写成一长串内联命令（Windows 侧引号/中文极易被吞）。

## 2. Windows 本机的编码坑（踩过两次，会毁文件）

1. **绝不要**用 `Get-Content -Raw` + `Set-Content -Encoding utf8` 往返 UTF-8 中文文件：
   PowerShell 5 会按 ANSI 读，写出双编码乱码，甚至把 `"` 吃掉导致脚本语法坏掉。
   ⇒ 一律用 read / edit / write 工具改文本文件。
2. here-string `@'…'@` 里 `\n` 不会展开（会原样写进 .py/.sh）；用 write 工具或真换行。
3. PS 5 没有 `-Encoding utf8NoBOM`；写 Unix 脚本用
   `[IO.File]::WriteAllText($p, ($s -replace "`r`n","`n"), (New-Object System.Text.UTF8Encoding($false)))`。
4. 命令里带中文引号/圆括号的长字符串会被 PS 解析吞掉 ⇒ 复杂命令先落成文件再执行（本仓库 `_work/*.ps1` 就是干这个的）。

## 3. Ascend / NPU 算子（aclnn WQBM 系）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `antiquant_scale` dtype | 报 `161002 x's dtype must be same as antiquantScale's` | scale 必须与 x **同为 bf16**（曾把 fp16 当"不支持 per-group"） |
| x 维度 | 只吃 2-D | 3-D 会报 `x dim should be [2,2]`；批量要走 **GroupedMatmulV5** |
| N 上限 | 65535 | lm_head(248k) 要切段（本仓库切成 4×62080） |
| 单次调用成本 | — | **约 50 µs 且对 M 几乎不敏感**（M=1 与 M=128 在 N=1280 上都是 0.05 ms）⇒ 优化目标是"少调用/提高单次利用率"，不是省带宽 |
| GMM 工作区 | 512 专家曾申请 1.58 GiB | 限制每次处理的专家数，并把**驱动工作区**计入显存（只看 torch allocated 会误判） |
| `int64` ArgSort | 悄悄退到 AI CPU | 专家 id 只有 0..511，转 fp32 再排 |
| 图捕获 | 捕获失败/结果错 | 位置张量必须进图（设备端），host 侧分支/每步新建 `arange` 会破坏捕获 |
| 单进程跨卡捕获 | dev1 图永远错 | dev1 不可在单进程里捕获 ⇒ 改成**每卡一个进程**（r54/55 的 24+24） |

## 4. 数值 / 正确性

1. **bf16 归约顺序差 1 ulp 会被 MoE topk 放大**：conv 的 `(buf*w).sum(-1)`（成对归约）与
   `w0*x0+w1*x1+…`（左结合）差 1 ulp → logits 偏 6.9e-2、argmax 变化。两条路径必须同一种写法。
2. **验证"逐位一致"必须用非零状态**：`pos=0`（S 全零）会掩盖一切归约差异，当时 48 层全"精确"是假象。
3. `rms_norm()` 是 **(1+weight)** 语义；要"直接乘"必须预存 `w-1`（否则 nll 从 2.17 炸到 2.52）。
4. 任何量化/布局/拼接改动都要过**配对 NLL/KL/top1 + 任务级门禁**（MCQ、长文检索），不能只看 HTTP 200。
5. 分块 prefill 必须配**分块图捕获**才有收益（无图版比逐 token 慢 1.23×，r49 加图后 2.1×）。

## 5. 服务与运维

1. **`systemctl stop` 杀不到容器内的推理进程**：`docker exec -d` 起的进程不在 systemd cgroup 里。
   ⇒ 显式 `docker exec fnx bash -lc "pkill -9 -f '[p]ython -m fnx.server'"`，再轮询 `npu-smi info` 确认显存真释放。
2. **流式客户端中途断开** ⇒ 服务端仍持全局生成锁，`/health` 一起阻塞 ⇒ 只能重启（`kill -9`）。客户端必须读满 `[DONE]`。
3. **报速度前先确认跑的是哪份启动脚本**：`pgrep -af` 会打印完整环境。曾因 `p275.sh` 被改成
   `-g128` + `DEQ_ATTN=10`，造出 TPOT 64→74 ms、显存 58.97→59.53 GiB 的"假回归"。
4. **vLLM**：`max_model_len` 与请求 `max_tokens` 共享预算（`32768` 上下文 + `max_tokens=32768` ⇒ 400）；
   `/health` 返回空 200（探针用 `/v1/models`）；MindIE/msModelSlim 的 w8a8 **无 loader** ⇒ 用 HF bf16。
5. 模型只能**二选一常驻**（每卡约 60 GB，Flash-Next 52–57 GB、27B 57 GB）⇒ 用 `modelctl.sh` 切换。

## 6. 测量方法论（决定优化方向对不对）

1. **算子级测量必须独占卡 + `with torch.npu.device(dev)`**：在生产共享的 npu:1 上测出的数虚高 1.8×，差点得出"固定开销 0.6 ms"的错结论。
2. **TTFT 必须用唯一 prompt**：同一 prompt 连发会命中前缀缓存，测出 58 ms 的假 TTFT；要同时报 cold/warm 两档。
3. 先用微基准判瓶颈类型（带宽 / 调用数 / Cube 利用率），再决定优化；本项目的真相是
   **调用数 × ~50 µs**，不是带宽。
4. **负结果也要入库**，否则后人会重踩：MIX kernel（GM 往返吃掉收益）、`addcmul` 注入、
   head int8 分块、DeltaNet 5-D 广播、`FNX_MOE_FAST` 减算子（图内零收益）、per-expert 分组的 MoE（更慢 3.7×）。

## 7. 评测 harness 的坑（LiveCodeBench）

1. `testtype="script"` 需要 `grade_script`（原版 `testing_util.py` 没有）——humanevalplus/mbppplus 全靠它。
2. 官方测试脚本 `import numpy`，而**宿主机 python3 没有 numpy** ⇒ 判题必须在容器 venv 里跑。
3. `ProcessPoolExecutor` + `subprocess(preexec_fn=…)` 会产生**假 runtime 失败** ⇒ 复判要串行（`rejudge2.py`）。
4. **MBPP+ 题面/判题不一致**：题无 `starter_code` ⇒ 提示词退化成"读 stdin"，判题器却按脚本调用**具名函数** ⇒
   必然 NameError。修正提示词后同一模型 1/33 → 23/33。**评测前先验证协议自洽**。
5. 数据集（841 MB / 4.8 MB）刻意不入库；工具在 `tools/livecodebench/`。

## 8. 贴墙版十条

1. 先量再改；没有微基准就别说"瓶颈是带宽"。
2. 算子级测量要独占卡、设当前 device。
3. TTFT 用唯一 prompt，报 cold/warm 两档。
4. 报数字前 `pgrep -af` 确认跑的是哪份配置。
5. `systemctl stop` 不杀容器进程；停完看 `npu-smi`。
6. UTF-8 文件只用 read/edit/write 工具改。
7. 大文件走 SFTP；小文件分片名要零填充。
8. 改量化/布局要过 NLL+任务门禁，不只看 200。
9. 逐位一致用非零状态验证；归约顺序必须对齐。
10. 负结果写进文档，比"我们试过"更有价值。
