# Qwen3.8-Flash-Next 第 44 轮实测记录

> 主题：**长上下文能力测量（16k / 32k / 64k / 128k / 256k）**。
> 结论先说：**这台机器的硬上限是 16k**（16k 能起、32k 启动即 OOM）。16k 及以内的 prefill / decode / 端到端全部实测；32k–256k 给内存与时间的**推算**，并说明为什么不可达。

---

## 0. 一句话

**P（`FNX_CTX`）= 最大序列长度**，KV/rope/mask/图捕获都按它分配。实测：**2048 / 8192 / 16384 都能起，32768 直接 OOM**（还差 386 MiB，只剩 5 MiB）。所以 16k 是本机的硬上限；32k 起需要先省出显存。

## 2. KV 显存：算出来的和量出来的一致

本机 45 层在 dev0，其中 **11 层是全注意力**（`layer_types` 每 4 层一个 full）。每 token 每层 K+V = `2 头 × 256 × 2 B × 2` = **2 KB** ⇒ **22.5 KB/token**（11 层）。

| P | KV 合计 | 与实测对照 |
|---:|---:|---|
| 2048 | 47 MB | 实测基线 58.97 GiB |
| 8192 | 184 MB | 实测 59.10 GiB（+133 MB ≈ 计算值 138 MB）|
| 16384 | 369 MB | 实测 59.27 GiB（+307 MB ≈ 计算值 322 MB）✅ |
| 32768 | 738 MB | **OOM**（差 386 MiB）|
| 65536 | 1.48 GB | 不可达 |
| 131072 | 2.95 GB | 不可达 |
| 262144 | 5.90 GB | 不可达 |

48 层权重常驻已占 **58.5 GiB**，只剩约 2 GiB 给 KV + 图池 + 前缀缓存；**16k 之后的 0.3 GiB 余量是硬墙**。

## 3. 时间维度：prefill 才是真正的天花板

实测 prefill 速率随长度缓慢上升（61.7 → 70.7 ms/token），因为每 token 要做 `O(P)` 的注意力 + **`O(P)` 的 KV 写入**（当前实现用 one-hot 广播整块 cache，是为了图捕获安全，代价是每步读写整块）。拟合：

```
每 token 平均 = 60.9 + 0.000613 × n   (ms)     # 用 8026/16021 两点拟合，回代 16k 误差 2.6%
```

| 上下文 | prefill 单 token（推算） | **prefill 总耗时** | TPOT（推算） | 端到端（+16 token） |
|---:|---:|---:|---:|---:|
| 1,110 | 60.8（实测） | 67.3 s（实测） | 67.3 ms（实测） | 68.3 s |
| 8,026 | 65.8（实测） | 528 s（实测） | 73.1 ms（实测） | 529 s |

## 4. 为什么 32k–256k 不可达（三条独立原因）

1. **显存**：KV 需要 738 MB / 1.48 GB / 2.95 GB / 5.90 GB，而可用余量只有约 0.3 GiB。
   - 缓解 1：**KV 用 int8**（本卡无 FP8）可减半 ⇒ 32k 变 369 MB（**能装**），64k 变 738 MB（仍超），128k/256k 依旧不可达。
   - 缓解 2：把 KV 放主机内存 ⇒ 每 token 要过 PCIe 读 5.9 GB（21 GB/s）≈ 280 ms/token，比算还慢，否决。
   - 缓解 3：减少单卡层数 ⇒ 需要更多卡，不是单机问题。
2. **时间**：即使显存够，256k 的 prefill ≈ **16 小时**（本机 prefill 约 15 token/s）。要实用必须做分块 prefill（第 36 轮实测稠密 31.9× / MoE 1.54×，推算整体 2–2.5×）——那也只能到 ~8 小时，仍不实用。
3. **模型语义**：本模型在 `indexer_budget = 2048` 之外是**稀疏选块注意力**（config 里有 `indexer_head_dim / indexer_kv_heads / indexer_n_heads`）。我们的实现是**稠密 causal**（`engine.py` 顶部注释已写明"indexer 暂未实现，≤2048 与参考逐位一致"）。所以 **>2048 的数值与模型设计不一致**：本轮的 16k 数字是"我们这套稠密实现"的性能，不是"模型该有的长上下文行为"。要真正支持长上下文，必须先实现 indexer。

## 5. 生产恢复

测量完已把服务切回 `FNX_CTX=2048` 并交回 systemd：`active`、watchdog 在跑、dev0 58.97 GiB、`/health` ok。**生产不建议开大 CTX**：KV 与会把图池挤爆（32k 启动失败就是证据）。

## 6. 复现

```bash
# 起一个大 CTX（16k）
CTX=16384 bash /root/ascend-dev/p332.sh          # 期望 ready，hbm0 ≈ 59.27 GiB
cd /root/ascend-dev && python3 p333.py 16384     # ≈19 分钟
# 期望：n_prompt≈16025  TTFT≈1133 s (70.7 ms/tok)  TPOT@16k≈74 ms

```
