# Qwen3.8-Flash-Next 第 31 轮实测记录

> 本轮的目标：**多请求批处理（batching）能不能把吞吐抬起来**。
> 结论先说：**批处理机制已经做完并验证正确，但在当前硬件/实现下收益有限（B=2 只有 1.43×），
> 而且单请求延迟会变差 38% ⇒ 生产保持 B=1，代码留在 `FNX_BATCH` 开关后面。**

---

## 0. 一句话结论

| 项 | 结果 |
|---|---|
| 微基准（孤立 int8 GEMM） | 单次调用耗时**与 B 无关**（B=1 0.20 ms / B=32 0.19 ms）⇒ 理论上可摊 8–32× |
| 真实模型 B=2 | 每步 **196–203 ms**（B=1 是 142.9）⇒ 只多花 57 ms，**约 60% 可摊薄** |
| 端到端等价性 | B=1 → `mean_nll 2.1756`（与改造前**逐位相同**）；B=2 → 2.1693（差 0.006，bf16 行批舍入） |
| B=4 | **OOM**（dev0 已 60.31/60.96，40 个专家行的解包还要 126 MB）；要跑得把 `LPC` 降到 45（+12 ms/步） |
| 吞吐投影 | B=2 双并发 **1.43×**；B=4 四并发约 **1.82×**（要 LPC=45） |
| 单人代价 | B=2 时单请求每步 +38%（196 vs 143） |
| **决策** | **生产保持 B=1**；B>1 代码保留（`FNX_BATCH`），等"多客户端并发"成为真需求再上调度器 |

## 1. 为什么一开始很乐观：微基准

`tests/t_batch_micro.py`（只分配几十 MiB，不停服务）：

| 权重 | B=1 | B=2 | B=8 | B=32 |
|---|---|---|---|---|
| `w_qkv` 类（int8 25 MiB, K=2560 N=10240） | 0.20 ms | 0.19 | 0.19 | 0.19 |
| `gate_w` 类（int8 1.2 MiB, K=2560 N=512） | 0.18 ms | 0.18 | 0.18 | 0.18 |
| 参照：同尺寸纯 bf16 matmul | 0.04 ms | — | 0.04 | — |

**结论：int8 路径的成本 = "把整块权重反量化一次"，与行数无关；真正的 matmul 几乎免费。**
如果整层的成本都是这样，B=8 就该有 8×。但下一节说明为什么不成立。

## 2. 批维改造（`FNX_BATCH`，默认 1）

| 文件 | 改动 |
|---|---|
| `engine.py` | 新增全局 `B`；`FnLayer.S/conv/ple_conv`、`KVStore.k/v` 全部加批维；`_deltanet` 用 `h.shape[0]` 推导批大小（`S` 改成整批张量参与运算）；`_qsa` 逐行 `pos` + 逐行 one-hot 写 KV + 逐行 mask + `rope_cs` 支持 `[B]`；`_moe` 把 `b×TOPK` 个 (token,专家) 摊平成一次 gather + 两次 GEMM；`gated_residual`/`inject` 推导批维 |
| `model.py` | `tok/pos0/pos1/emb_buf/h0/h1/logits/ngram_emb/h_host` 加批维；`embed_rows`（批量取嵌入行）；`step(tok|list)`；`step_pad`（单序列在 B>1 上的兼容入口：token 复制到所有行）；`row_logits(i)`；**`zero_row(r)`**（只清一行，其它行不受影响——连续批处理的前提） |
| `server.py` | 单序列路径（generate / `/fnx/loss` / `/fnx/selfcheck` / 前缀构建）统一走 `step_pad` + `row_logits(0)` |

**关键设计**：批内的行**完全独立**（各自的 `S`/`conv`/kv/`pos`），所以"把同一 token 复制到所有行"
等于把这一行的计算重复 B 次，第 0 行的结果与 B=1 时一致 —— 这就是等价性验证的原理。

---

## 3. 等价性验证（上线前提）

| 配置 | `mean_nll` | top1 | 与 B=1 基线差 |
|---|---|---|---|
| B=1（改造后） | **2.1756** | 49.00% | **0**（逐位相同） |
| B=2 | 2.1693 | 48.50% | −0.006 nats |

差 0.006 来自 bf16 GEMM 行批的舍入顺序变化，远小于 0.05 的验收线。
**B=1 完全不变**这一点很重要：说明批维改造没有动到既有数值路径。

---

## 4. 真实成本：为什么不是 8×

在 B=1 的生产口径下（142.9 ms/步，分解见第 30 轮 §16）：

| 部分 | 每步耗时 | 是否随 B 增长 |
|---|---|---|
| 稠密权重反量化/读入 | ≈ 86 ms | **不增长**（微基准证明） |
| MoE 专家 gather + 两次 GEMM | ≈ 55 ms | **随 B 增长**（每 token 各自的 top-10） |
| attention（KV 写 + att matmul + 逐行 mask） | ≈ 45 ms | **随 B 增长** |
| head（mixer + lm_head 606 MiB int8） | ≈ 8 ms | 不增长 |

实测验证：B=2 每步 196–203 ms ≈ 143 + 57 —— 正好是"1 行的成本 + 约半行的边际成本"。
**可摊薄约 60%，随批线性约 40%。** 微基准里"行免费"只在孤立 GEMM 上成立，
一旦放回整层（MoE 路由 + attention），行是有真实成本的。

## 5. 吞吐投影与单人代价

| 配置 | 每步 | 每 token（并发满载） | 吞吐提升 | 单人延迟 |
|---|---|---|---|---|
| B=1 | 142.9 ms | 143 ms | 1.00× | 基准 |
| B=2 | ~200 ms | 100 ms | **1.43×** | **+38%** |
| B=4（需 LPC=45） | ~314 ms | 78.5 ms | 1.82× | +120% |
| B=8（需 LPC≤43） | ~500 ms | 62.5 ms | 2.29× | 更差 |

B=4 在 `LPC=46` 直接 **OOM**（`_deq_v2` 要 126 MB，只剩 2.63 MiB）。
要跑 B=4 得把一层捕获换成 eager（`LPC=45`），对所有请求 +12 ms/步。

## 6. 为什么本轮没有继续做调度器

要让 B>1 真正生效，需要**连续批处理**调度器（设计已定）：
- 每个槽占一行；`zero_row(r)` 让新请求从干净状态开始，不影响正在解码的其它行；
- 单线程循环：每步给每一行喂"它自己的下一个 token"（prefill 阶段喂 prompt token，decode 阶段喂上一步采样结果），
  **不做 padding、不污染状态**；
- 流式：每个槽一个 `queue.Queue`，SSE 生成器从中取 token。

但它和两个现实冲突：
1. **单人代价 +38%**（B=2），而当前就是单用户交互场景 —— 直接上就是回归；
2. 投影收益只有 1.43×（B=2）/1.82×（B=4），而 B=4 还要牺牲一层捕获。

**收益 < 复杂度 + 回归风险，所以停在"机制就绪 + 数据齐全"这一步**，
等真实出现 ≥3 个并发客户端再花 1–2 小时接调度器。
