# 910B4 模型启停脚本 `modelctl.sh` 说明

日期：2026-11-01
位置：服务器 `192.168.18.206` 的 `/root/ascend-dev/modelctl.sh`（配置 `/root/ascend-dev/models.json`）
本仓库副本：`scripts/modelctl.sh`、`scripts/models.json`

用途：**按配置选择启动哪个模型**。同一时刻只跑一个（两张 910B4 共 128 GB，见 §5），
脚本负责"停掉旧模型 → 确认显存释放 → 启动新模型 → 等健康检查通过 → 打印状态"。
目前配置里有两个可选模型：

| 名字 | 类型 | 模型 | 权重 |
|---|---|---|---|
| `flash-next` | `fnx`（自研引擎） | `qwen3.8-flash-next-w4` | `/models/Qwen3.8-Flash-Next-LQP*`（W4，MoE 121B） |
| `27b` | `vllm`（vLLM-Ascend 0.23.0） | `qwen3.8-27b` | `/models/Qwen3.8-27B`（bf16，52 GB） |

## 1. 命令

```bash
/root/ascend-dev/modelctl.sh list                 # 列出配置里的模型
/root/ascend-dev/modelctl.sh status               # 现在跑的是哪个 / 端口 / model id / NPU 进程
/root/ascend-dev/modelctl.sh start <模型>          # 停掉其它模型 → 等显存释放 → 启动 → 等健康检查
/root/ascend-dev/modelctl.sh stop [模型]           # 停指定模型；不给参数=停全部
/root/ascend-dev/modelctl.sh restart <模型>        # 等价 start（start 内部已先 stop 全部）
/root/ascend-dev/modelctl.sh logs <模型> [行数]     # 看本次启动日志（默认 40 行）
```

示例：

```bash
# 切到 27B（约 4 分钟：停 fnx + vLLM 启动与图编译）
/root/ascend-dev/modelctl.sh start 27b

# 切回 Flash-Next（约 3.5 分钟：装配 + 前缀缓存 + 图捕获）
/root/ascend-dev/modelctl.sh start flash-next

# 看当前状态 / 启动日志
/root/ascend-dev/modelctl.sh status
/root/ascend-dev/modelctl.sh logs 27b 60
```

## 2. 配置文件 `models.json`

```json
{
  "default_port": 8000,
  "defaults": { "health_timeout_s": 900, "stop_timeout_s": 90 },
  "models": {
    "flash-next": {
      "kind": "fnx",
      "desc": "Qwen3.8-Flash-Next 121B MoE W4，自研 fnx 引擎（r55）",
      "model_id": "qwen3.8-flash-next-w4",
      "port": 8000,
      "systemd": "fnx.service",
      "health": "/health",
      "start_log": "/root/ascend-dev/logs/modelctl-flash-next.log"
    },
    "27b": {
      "kind": "vllm",
      "desc": "Qwen3.8-27B dense bf16，vLLM-Ascend 0.23.0，TP=2",
      "model_id": "qwen3.8-27b",
      "model_path": "/models/Qwen3.8-27B",
      "port": 8000,
      "tp": 2,
      "max_model_len": 32768,
      "gpu_memory_utilization": 0.9,
      "devices": "0,1",
      "vllm_args": "--trust-remote-code --limit-mm-per-prompt '{\"image\": 0, \"video\": 0}'",
      "health": "/v1/models",
      "start_log": "/root/ascend-dev/logs/modelctl-27b.log"
    }
  }
}
```

字段说明：

| 字段 | 适用 | 含义 |
|---|---|---|
| `kind` | 必填 | `fnx`（走 systemd 单元）或 `vllm`（`vllm serve`） |
| `model_id` | 必填 | 对外暴露的 model 名（`/v1/models` 里的 id） |
| `port` | 可选 | 服务端口，默认取顶层 `default_port`（8000） |
| `health` | 可选 | 健康检查路径：fnx 用 `/health`，vLLM 用 `/v1/models`（vLLM 的 `/health` 返回空 200） |
| `systemd` | `fnx` 必填 | 启动用的 systemd 单元名（`fnx.service`，其 `ExecStartPre` 会跑 `p275.sh`） |
| `model_path` | `vllm` 必填 | 权重目录（HF 格式 safetensors） |
| `tp` / `max_model_len` / `gpu_memory_utilization` | `vllm` | 直接透传给 `vllm serve` |
| `devices` | `vllm` | `ASCEND_RT_VISIBLE_DEVICES`，默认 `0,1` |
| `vllm_args` | `vllm` | 追加参数，原样拼进命令行（可含带引号的 JSON，如 `--limit-mm-per-prompt`） |
| `start_log` | 可选 | 启动日志路径；`logs` 子命令读它 |
| `health_timeout_s` / `stop_timeout_s` | 可选 | 健康检查等待上限 / 停服务后等显存释放的上限 |

**新增一个模型**：在 `models` 里加一段即可，例如再加一个 vLLM 模型：

```json
"qwen-其他模型": {
  "kind": "vllm", "model_id": "my-model", "model_path": "/models/xxx",
  "tp": 2, "max_model_len": 32768, "devices": "0,1",
  "vllm_args": "--trust-remote-code", "health": "/v1/models",
  "start_log": "/root/ascend-dev/logs/modelctl-my-model.log"
}
```

## 3. 脚本做了什么（执行顺序）

`start <模型>`：

1. 解析配置，打印目标（kind / model_id / port）；
2. **停掉所有模型**：
   - `fnx`：`systemctl stop fnx.service` + `pkill watchdog.sh` + **容器内** `pkill -9 -f '[p]ython -m fnx.server'`；
   - `vllm`：容器内 `pkill -f 'vllm serve'`（3 s 后再 `-9`）；
3. 轮询 `npu-smi info` 直到**没有任何进程占卡**（默认最多 90 s），否则报错退出；
4. 按 `kind` 启动：
   - `fnx`：`systemctl start fnx.service`（内部会跑 `p275.sh` 并自己等就绪）；
   - `vllm`：`docker exec -d fnx bash -lc "ASCEND_RT_VISIBLE_DEVICES=… vllm serve … > 日志 2>&1"`；
5. 轮询健康检查 `http://127.0.0.1:<port><health>` 返回 200（默认最多 900 s）；
6. 打印状态（谁在跑、model id、`/health`、NPU 进程与占用）。

失败时会把日志末尾 20 行打到 stderr，便于直接看原因。

## 4. 实测耗时（2026-11-01 验证）

| 操作 | 耗时 | 结果 |
|---|---:|---|
| `start flash-next`（从 27B 切来） | **3 min 28 s** | `/v1/models` → `qwen3.8-flash-next-w4`，`/health` ok，两卡 52/54 GB |
| `start 27b`（从 fnx 切来） | **3 min 56 s** | `/v1/models` → `qwen3.8-27b`，两卡各 57 GB |
| `status` | <1 s | 正确显示运行中引擎、model id、NPU 进程 |

两条路径都实测通过（`list/status/stop/start/restart/logs` 全部可用）。

## 5. 为什么必须"一次只跑一个"

两卡共 128 GB（每卡 64 GB 可用约 60 GB）：

| 模型 | 每卡占用 |
|---|---:|
| Flash-Next（W4 MoE 121B，r55 双进程流水 24+24） | 52–57 GB |
| Qwen3.8-27B（bf16，TP=2） | 57 GB |

两者同时常驻需要 >110 GB/卡，放不下。⇒ 脚本在 `start` 前强制 `stop` 全部，属于设计而非限制。

## 6. 已知坑（脚本已内置处理）

1. **`systemctl stop` 不会杀容器内的推理进程**：`docker exec -d` 起的进程不在 systemd cgroup 里，
   停服务后显存仍占着。脚本里显式 `docker exec … pkill -9`，并轮询 `npu-smi` 确认释放。
2. **vLLM 的 `/health` 返回空 200**：`curl` 取不到 body，所以配置里 vLLM 用 `/v1/models` 做健康检查。
3. **vLLM 的 `max_model_len` 与请求 `max_tokens` 共享预算**：`max_model_len=32768` 时，
   `max_tokens=32768` 的请求会被 400 拒绝。要更长输出就把 `max_model_len` 调大（重启生效）。
4. **首次启动含图编译**：vLLM 首次 `torch.compile`/图捕获约 2–4 min；fnx 冷启动约 3.4 min。
   健康检查超时默认 900 s，够用。
5. **27B 默认会输出思考链**：请求里带 `{"chat_template_kwargs": {"enable_thinking": false}}`
   可关闭（与 Flash-Next 的 `FNX_ENABLE_THINKING=0` 对齐）。

## 7. 常用排查

```bash
/root/ascend-dev/modelctl.sh status                 # 谁在跑
/root/ascend-dev/modelctl.sh logs 27b 80            # 27B 启动日志
tail -f /root/ascend-dev/logs/server.log            # fnx 引擎日志
npu-smi info | tail -8                              # 显存与进程
curl -s http://127.0.0.1:8000/v1/models | head -c 200
```

如果脚本报"显存未在 Xs 内释放"：手动 `docker exec fnx bash -lc "pkill -9 -f '[p]ython -m fnx.server'; pkill -9 -f 'vllm serve'"`，
再用 `npu-smi info` 确认，然后重跑 `start`。
